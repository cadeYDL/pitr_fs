# pitr-fs I/O 与恢复性能实测

## 测试口径

- Linux 虚拟机，普通文件系统为 Btrfs，pitr-fs 使用本地 JuiceFS file 后端。
- fio 使用 `psync`、`iodepth=1`、`direct=1`，独立运行 3 轮并取中位数。
- 顺序写每轮完整写入一次文件；随机读写使用 4 KiB block 和固定 I/O 数。
- 小、中、大、超大文件分别为 4 KiB、1 MiB、256 MiB、2 GiB。
- 恢复耗时包含 CLI、Docker exec 和 RPC 开销，每轮都逐文件校验内容与目录结构。
- JuiceFS 缓存位于独立卷，`--cache-size=1024` MiB。

小文件顺序读会在 4 KiB 文件上重复读取固定总量，主要反映单次 FUSE/元数据
路径开销，不应解读为持续大文件带宽。大文件顺序写保留普通文件系统的
74%–86%，是当前表现最好的一类；4 KiB 随机写只有约 1.3–1.5 MiB/s，是最
主要的前台性能瓶颈。顺序读约为普通文件系统的 16%–18%，仍有明显优化空间。

## 恢复性能

| 场景 | 变更对象 | 中位数 ms | 最小 ms | 最大 ms | 三轮校验 |
|---|---:|---:|---:|---:|:---:|
| 单个 256 MiB 文件 | 1 | 31.57 | 31.50 | 35.43 | 通过 |
| 1000 文件全部修改 | 1000 | 2503.41 | 2134.30 | 2793.29 | 通过 |
| 600 文件：修改、删除、新增 | 600 | 524.12 | 379.32 | 703.32 | 通过 |
| 多层目录树 1000 文件 | 1000 | 1299.93 | 1053.33 | 1946.08 | 通过 |

单个 256 MiB 文件恢复只回放 5 行元数据历史，耗时约 32 ms，证明恢复耗时主要
由历史行数而不是文件内容大小决定。1000 文件全量修改需要回放 3000 行历史，
中位数约 2.5 秒。

## 测试中发现并修复的问题

1. JuiceFS 默认读缓存上限为 100 GiB，且宿主 `df` 不能感知容器或虚拟机实际
   配额。缓存增长后会先触发 ENOSPC，使 PostgreSQL 进入恢复并让 fio 或
   `touch` 卡在 FUSE 请求。现在安装器使用独立缓存卷，默认限制为 1024 MiB。
2. JuiceFS 对部分 unlink 异步删除 chunk。原实现依赖 chunk DELETE 触发器，
   auto 窗口关闭后执行的异步删除无法归属版本，恢复时会得到长度正确但内容为
   零的稀疏文件。现在 node DELETE 会主动快照尚存 chunk 并持有 slice pin；
   混合恢复和目录树恢复连续三轮全部通过。

原始结果由 `bench/bench-io-recovery.py` 逐项写入 `io-raw.json`、
`io-median.json`、`recovery-raw.json` 和 `REPORT.md`。脚本支持 `--skip-io`
在保留 I/O 结果后用干净实例续跑恢复测试。
