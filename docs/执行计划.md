## 0. 协作流程与约定

**当前交付方式**:
- Codex 负责生产代码、单元/集成/E2E/基准测试、文档与 calw 部署。
- 用户在所有 Phase 完成并保持最终挂载运行后做最终验收。

**工作流**:每完成一个 Task,用户通知,我按 Task 的"验收清单"补测 + review;通过后进下一个 Task。**不要多 Task 并行**——review 反馈的偏离设计问题往往牵动多个 Task。

**Task 状态**:直接改本文档,标记 `TODO / DOING / REVIEW / DONE`,便于同步。

**代码分支**:一期主干开发,每个 Task 一个 commit,commit message 前缀 `[Task X.Y]`。

**通用验收基线**(所有 Task 隐含要求,不再单列):
- `go vet ./... && go build ./...` 通过;
- 关键路径有 error 处理,不用 `panic` 除非明确合理;
- 日志走结构化(建议 `slog` 或 `zap`);
- 不添加不必要的注释、抽象、feature flag。

**依赖图**:

```
P0 (可行性)  ─┐
              ▼
P1 (骨架)  ─► P2 (gRPC + PG + txn)  ─► P3 (FUSE)  ─► P4 (revert)  ─► P5 (SDK)  ─► P6 (集成 + bench)
```

### Task 3.2: `versionedHook` 拦截模板 [DONE]

- **目标**:实现设计文档 §5.3 的 5 步拦截逻辑,所有写类 handler 都调它。
- **参考**:设计文档 §5.3
- **产物**:`internal/proxy/hook.go`
- **关键接口**:
  ```go
  type Node struct {
      fs.LoopbackNode
      root *Loopback
      mgr  *txn.Manager
  }

// 命中 active txn → 打开唯一 auto 窗口 + 执行 JuiceFS action + 关闭窗口
  // 未命中 → 直接 action
  func (n *Node) versionedHook(
      ctx context.Context,
      absPath, cmd string,
      fd uint64,                     // 用于去重,0 表示无 fd
      action func() syscall.Errno,
  ) syscall.Errno
  ```
- **fd 生命周期窗口**:`map[fd → auto_version_id]` 由 mutex 保护。事务内可写
  fd 从 Open 到 Release 持有一个 auto window,后续 Write/Flush/mmap 脏页
  共用该版本;底层 Release 完成后才关闭 auto,确保 JuiceFS 延迟提交的 chunk
  元数据也被捕获。无 active 事务的 fd 缓存负判定。开放写 fd 未释放时
  commit/rollback 最多等待 2 秒,随后明确拒绝。
- **验收清单**(**我会补**,用 mock 的 mgr + 真实 PG):
  - [x] `TestHook_NoActiveTxn_PassThrough`
  - [x] `TestHook_ActiveTxn_CreatesAutoVersion`
  - [x] `TestHook_FdDedup`:同 fd 二次调用,pitr_txn 只多一条 auto
  - [x] `TestHook_PGFail_ReturnsEIO`
  - [x] `TestHook_ActionFail_RollsBackVersion`:action 报错 → auto 版本也回滚
- **实现结论**:按 P0.3 结论使用“独立事务 + 唯一开放 auto 窗口”。数据库
  唯一索引和 daemon 全局互斥共同保证单 daemon 归属确定;失败时
  `pitr_abort_auto` 只 replay 失败 auto,不影响同 parent 的其他版本。

## 使用建议

- 一次做一个 Task,做完在**表格里改状态为 REVIEW**,告诉我 "Task X.Y 可 review"。
- 我做的事(按顺序):
  1. 对照设计文档 + 本文的"关键接口 / 数据结构"和"验收清单",逐项 review 代码
  2. 补该 Task 列出的所有单测/集成测试
  3. 反馈:偏离项 + 建议 + 测试结果
  4. 全部通过 → 表格改 DONE,进下一个 Task

- Task 里如果有**依赖**没完成,不要跳。Task 0.3 的结论会影响 2.2/2.3 的实现,不要先跳去写 2.3。
