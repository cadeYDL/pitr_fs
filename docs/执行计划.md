# PITR-FS 执行计划

配合 [设计文档.md](./设计文档.md) 使用。设计文档说的是"要建成什么样",本文说的是"怎么一步步建"。

---

## 0. 协作流程与约定

**分工**:
- 用户负责实现所有生产代码(Go / Python / Shell / SQL)。
- 我负责根据本文档:补单元测试与集成测试;对提交的代码做 review。

**工作流**:每完成一个 Task,用户通知,我按 Task 的"验收清单"补测 + review;通过后进下一个 Task。**不要多 Task 并行**——review 反馈的偏离设计问题往往牵动多个 Task。

**Task 状态**:直接改本文档,标记 `TODO / DOING / REVIEW / DONE`,便于同步。

**代码分支**:一期主干开发,每个 Task 一个 commit,commit message 前缀 `[Task X.Y]`。

**通用验收基线**(所有 Task 隐含要求,不再单列):
- `go vet ./... && go build ./...` 通过;
- 关键路径有 error 处理,不用 `panic` 除非明确合理;
- 日志走结构化(建议 `slog` 或 `zap`);
- 不添加不必要的注释、抽象、feature flag。

**依赖图**:

```
P0 (可行性)  ─┐
              ▼
P1 (骨架)  ─► P2 (gRPC + PG + txn)  ─► P3 (FUSE)  ─► P4 (revert)  ─► P5 (SDK)  ─► P6 (集成 + bench)
```

### Task 2.2: `internal/pg` — PG 连接封装 [TODO]

- **目标**:提供事务封装 + `SET LOCAL` 语义,是所有 pitr 逻辑的地基。
- **产物**:`internal/pg/{connect.go, tx.go, errors.go}`
- **关键接口**:
  ```go
  package pg

  type DB struct { /* pool */ }
  func Connect(ctx context.Context, dsn string, opts ...Option) (*DB, error)
  func (db *DB) Close() error
  func (db *DB) Ping(ctx context.Context) error

  // InTx 在事务里跑 fn;panic 或 error 都会 rollback
  func (db *DB) InTx(ctx context.Context, fn func(Tx) error) error

  type Tx interface {
      Exec(ctx context.Context, sql string, args ...any) (RowsAffected int64, err error)
      Query(ctx context.Context, sql string, args ...any) (Rows, error)
      QueryRow(ctx context.Context, sql string, args ...any) Row
      SetLocal(ctx context.Context, key, val string) error   // SET LOCAL <key> = <val>
  }
  ```
- **实现要求**:
  - 用 `pgx/v5` 连接池,不用 `database/sql`(需要 `SET LOCAL` 精确控制连接生命周期)
  - `InTx` 里必须**在同一 pgx.Conn** 上完成所有操作(重要,Task 0.3 结论决定是否用同一连接给 JuiceFS)
  - 失败时保留原始 PG 错误码(用 `errors.As` 可取到 `*pgconn.PgError`)
- **验收清单**(**我会补的单测,依赖 dockertest 或本地 PG**):

  - [ ] `TestInTx_Commit`:fn 返 nil → 事务提交

## 使用建议

- 一次做一个 Task,做完在**表格里改状态为 REVIEW**,告诉我 "Task X.Y 可 review"。
- 我做的事(按顺序):
  1. 对照设计文档 + 本文的"关键接口 / 数据结构"和"验收清单",逐项 review 代码
  2. 补该 Task 列出的所有单测/集成测试
  3. 反馈:偏离项 + 建议 + 测试结果
  4. 全部通过 → 表格改 DONE,进下一个 Task

- Task 里如果有**依赖**没完成,不要跳。Task 0.3 的结论会影响 2.2/2.3 的实现,不要先跳去写 2.3。

- 遇到设计文档没说清的边界(比如 rename 跨 scope),先在 Task 里加 `# 决策:XXX` 注释,commit 时把决策同步到设计文档对应章节,而不是在代码里自作主张。
