# pitr-fs 性能瓶颈梳理

本文描述当前实现的主要性能成本、可观测指标和优化顺序。结论针对 Linux 上
“用户 FUSE → pitrd loopback → JuiceFS FUSE → PostgreSQL/对象存储”的完整
生产路径；不能用只测底层 JuiceFS 的结果代替。

## 结论

当前首要瓶颈是小文件和高频元数据操作，不是大文件读取。每个写操作需要建立
并关闭自动版本，且全局只允许一个开放写窗口；这会叠加 PostgreSQL 往返、
history 触发器写放大和两层 FUSE 上下文切换。历史 slice pin 又会在首次修改
chunk 时增加少量引用维护，但它只处理发生变化的 slice，不扫描对象存储。

GC 不在每次写入或版本裁剪的同步路径中。版本删除只更新引用并合并一条持久化
请求；后台 GC 才遍历 JuiceFS 元数据和对象后端。因此正常写延迟与对象总量
基本解耦，但 GC 执行期间新写窗口会等待维护锁，远端对象数量很大时会形成可见
的尾延迟。

## 瓶颈清单

| 优先级 | 路径 | 成本与增长方式 | 当前保护 | 建议指标 |
|---|---|---|---|---|
| P0 | 自动版本窗口 | 每个逻辑写至少打开、关闭各一次数据库事务；全局串行，吞吐上限受单次操作延迟约束 | 开放窗口保证触发器归属唯一 | open/close p50、p95、p99；锁等待；ops/s |
| P0 | 元数据 history | `jfs_node/edge/chunk/chunk_ref` 首次变化写完整旧行 JSONB，并维护索引与 WAL | 同版本同主键只记录一次 | history rows/op、bytes/op、WAL bytes/op |
| P0 | 双层 FUSE | syscall 经过 proxy 和 JuiceFS 两次用户态切换；写路径还需要 direct I/O/fsync 保证版本边界 | 换取透明 POSIX 和可见性一致 | syscall 延迟、上下文切换、CPU/op |
| P1 | PostgreSQL 延迟 | JuiceFS 元数据和 pitr 控制事务共享数据库；远端 PG RTT 会直接进入前台延迟 | 本地部署默认降低 RTT | SQL p95、连接池等待、锁等待、WAL flush |
| P1 | 保留裁剪 | 每次关闭版本都检查上限并按时间线删除超限记录；删除会触发 slice 解码和引用递减 | 默认仅 100 个版本，按版本增量处理 | prune ms、释放 slice 数、队列年龄 |
| P1 | 内容审计 | 从 `/proc` 取命令，并对少量内容做有界采样 | 每文件 4 KiB、每窗口 3×64 B，不做完整 diff | audit ms、采样命中率、失败率 |
| P1 | revert | 目录闭包解析和 PL/pgSQL 按历史行逆序回放，成本随目标之后的变更行数增长 | 只处理目标 scope，事务内原子 | replay rows、闭包 inode 数、revert ms |
| P1 | 对象 GC | `juicefs gc --delete` 会扫描元数据和对象；远端后端还受 LIST/DELETE RTT 与限流影响 | 请求去重、低频批量、可恢复队列、写窗口互斥；例行任务不 compact 当前 chunk | GC duration、scanned/deleted objects、queue age、错误数 |
| P1 | 空间高水位裁剪 | 超限时逐个删除最老版本并释放 pin，成本随本轮淘汰版本和 slice 数增长 | 不扫描对象存储；每次删除后增量重算 retained | pruned versions、released bytes/version、quota overshoot |
| P2 | 缓存策略 | 为保证 revert 后立即可见，保守缓存设置会降低重复读取和元数据查询命中率 | 正确性优先 | page/data/meta cache hit、read p95 |
| P2 | 启动恢复 | PostgreSQL 启动、schema 迁移、JuiceFS/FUSE 两层挂载串行发生 | 只在启动/恢复路径 | ready time、迁移时长、挂载重试数 |

## 生命周期实现的性能成本

slice pin 采用每版本一个 `bytea`，每个 slice 只增加 12 字节的紧凑记录
（`chunkid:uint64 + size:uint32`），避免“一 slice 一版本一行”的高行数模型。
`pitr_slice_ref` 仅对仍被历史引用的 slice 保留聚合行。每次首次捕获旧 chunk
需要：解码该 chunk 的 slice 列表、对每个 slice 更新一条聚合引用和一条
JuiceFS 引用、追加两个紧凑缓冲。版本删除执行相反操作。

该设计选择“引用准确、更新增量、GC 异步”：

- 不依赖对象存储 LIST 来判断可删对象，避免最终一致性或列举遗漏导致误删。
- 不为每个 block 建历史明细行，降低表、索引和 VACUUM 压力。
- 删除前必须成功释放全部引用；编码损坏或引用缺失会让事务失败，优先泄漏而非
  误删。
- GC 通过 JuiceFS 原生适配层执行，因此本地、用户挂载目录和远端对象存储的
  删除语义一致。

空间预测同样不扫描对象后端。`jfs_chunk_ref` 每次变化通过独立触发器把唯一
slice size 在 `retained` 与 `reclaimable` 两个计数间移动；普通写只增加常数
级计数更新。用户显式执行 `pitr space` 时，最多解析请求数量的版本 pin，判断
删除某版本后哪些 slice 的引用会归零。该查询成本约为所列版本的 pin 总数，
不会进入普通 write 延迟。

这是逻辑文件数据估算，不是对象后端账单的严格字节数。误差来自压缩、对象头、
最小计费单元、compact 临时对象和异步 GC。界面同时显示 reclaimable，使用户
能够区分“已经不再需要”和“物理上已经删除”。

代价是一次覆盖涉及很多 slice 时，数据库更新数仍与 slice 数线性增长；大范围
随机覆写和大量小 slice 是生命周期维护最差的负载。

## 当前基准证据

仓库现有生产报告记录过以下结果：元数据 create 从 `2.0749 ms/op` 增至
`10.1335 ms/op`（约 `+388%`），顺序写吞吐从 `1622.79 MiB/s` 降至
`1350.52 MiB/s`（约 `-16.8%`），顺序读约下降 `3.85%`，1 GiB 稀疏文件
回滚约 `270.76 ms`。这些数据来自生命周期 pin 实现之前，只能作为历史基线；
合入后应按 `bench/README.md` 连续跑三轮并取中位数。

新基准至少应同时记录：

1. `pitr_slice_pin` 字节数、`pitr_slice_ref` 行数和待处理 GC 队列年龄。
2. retained、reclaimable、GC 请求预计释放字节与后端实际 `du`/账单字节的误差。
3. 固定 `history-limit` 下持续覆盖同一文件，确认对象空间在 GC 后收敛。
4. 本地 volume、用户挂载目录和实际生产远端后端分别测试，不能外推。
5. 前台写入与 GC 并发时的 p99 延迟，以及 GC 单独运行的删除吞吐。

## 优化顺序

1. 先消除全局写串行：按 inode/scope 分片版本归属，并给触发器提供无歧义的
   上下文。这是收益最大、证明成本也最高的改造。
2. 合并自动版本 open/close 往返，批量裁剪；同时保持操作失败补偿和崩溃恢复。
3. 将 history 从完整 JSONB 改为稳定的二进制旧行或字段 diff，并做时间分区，
   降低 WAL、索引和 VACUUM 成本。
4. 把 revert 的逐行 PL/pgSQL 回放改为集合 SQL/批处理，为常用 scope 增加组合
   索引并限制长事务。
5. 为 GC 增加限速、空闲窗口调度和扫描进度指标；对象很多时按后端能力调整并发，
   不应简单无限提高 `PITR_GC_THREADS`。
6. 在证明回滚可见性不受影响后，逐项放宽 JuiceFS/FUSE 缓存配置。

任何优化都必须同时通过内容回滚、版本淘汰后对象回收、崩溃重试和开放写窗口
并发测试；吞吐改善不能以缩短可恢复历史或提前删除对象为代价。
