## 各 Phase 交付

### Phase 0：可行性与基线

- 生产栈重跑 demo §1–§7，八个关键机制全通过。
- v1/v2/v3 后 revert v1，`a.txt` 恢复为 `hello v1`，`b.txt` 消失。
- 四张 history 表均捕获事件并以 `txn_id` 精确归属。
- 补齐规模、吞吐、空间和版本切换四维追溯基线。

证据见 `demo/RUN_LOG.md`、`bench/BASELINE.md` 和 `docs/P0-report.md`。

### Phase 1：schema 与部署

- 幂等 PostgreSQL schema、四张核心 shadow history、触发器和 replay 过程。
- 多版本 revert、chunk/chunk_ref 内容历史和引用生命周期。
- Docker all-in-one 镜像、幂等 format/schema、持久化卷与安装/恢复脚本。

### Phase 2：控制面与事务

- protobuf/gRPC、unix socket、reflection、PG 连接与事务状态机。
- `daemon/init/mount/umount/status/recover/config` 全生命周期命令。
- `begin/commit/rollback/logs` 事务命令；active 事务阻止 umount。
- `init` 与部署分工已同步：首次 format 只在 entrypoint，RPC init 仅做幂等校准。

### Phase 3：FUSE 拦截

- go-fuse 双层透明代理覆盖全部写类操作。
- 可写 fd 从 Open 到 Release 共用唯一 auto window，覆盖顺序写和 writable mmap。
- 底层 Release 后才关闭窗口，避免 JuiceFS 延迟 chunk 元数据逃逸。
- 全局唯一窗口、失败补偿、跨 scope rename 目标归属和 commit 开放句柄保护。

### Phase 4：时间旅行

- 可撤销 revert、dry-run、子树 scope、锁与缓存一致性。
- revert 自身形成新版本，可继续向前/向后切换。
- logs、diff 与 recover 已接入 CLI/RPC。

### Phase 5：SDK

- Go SDK：unix gRPC client、事务对象与状态机。
- Python SDK：wheel、同步 client、context manager 和异常回滚。
- 两种 SDK 均通过真实 daemon/FUSE 验证。

### Phase 6：E2E、边界与基准

- Agent edit/rollback、v1/v2/v3 时间旅行、不同 scope 并发。
- writable mmap、跨 scope rename、Unicode 文件名、daemon crash/recover。
- 100,000 目录项最终轮：revert `725.274155ms`，恢复 100,000 项并完整清理；
  用例总耗时 `508.18s`。
- 生产 benchmark 独立三轮中位数：

| 指标 | plain | pitr | 退化/耗时 | 目标 | 结论 |
|---|---:|---:|---:|---:|:---:|
| 元数据创建 | 2.0749 ms/op | 10.1335 ms/op | +388.38% | ≤30% | 未达标 |
| 顺序写 | 1622.79 MiB/s | 1350.52 MiB/s | -16.78% | ≤10% | 未达标 |
| 顺序读 | 1444.85 MiB/s | 1389.17 MiB/s | -3.85% | ≤10% | 通过 |
| 1 GiB revert | — | 270.76 ms | 270.76 ms | ≤500ms | 通过 |

元数据与顺序写指标不作为当前性能承诺；优化方向已记录在

1. 非 TTY 执行 `pitr status` 成功，wrapper 仅在真实终端附加 `-it`。
2. `pitr init /workspace` 幂等成功。
3. 正式挂载完成 v1/v2，然后 revert v1：
   - `ready.txt` 恢复为 `pitr-fs ready on calw.orb.local`；
   - v2 新增的 `temporary.txt` 消失。
4. 显式 rollback 后 `rollback-probe.txt` 消失。
5. 优雅 `docker restart` 后 3 秒内恢复 socket、挂载和验收文件。
6. `SIGKILL` 后精确解绑失联挂载，再执行 `install.sh recover`：
   - 复用原容器、`pitr_pgdata` 和 `pitr_data`；
   - 改进后的 ready 检查等待真实 gRPC Status，3 秒完成；
   - 验收文件保留，随后新事务提交成功。
7. PostgreSQL 共 27 张表，4 个生产触发器名存在；最终 0 active transaction。

说明：显式 `docker kill` 是 Docker 的人工停止操作，`unless-stopped` 不会
代替管理员自动重启；此场景应调用 `install.sh recover`。非人工的进程异常
退出仍由 `unless-stopped` 管理。

## 相对路径补充验收

2026-07-31 在正式 `/pitr_fs/data` 挂载上补充验证：

```bash
cd /pitr_fs/data/relative-e2e/nested
pitr begin .. -m 'relative path e2e'
pitr commit .././ -m 'relative path committed'
pitr logs ..
pitr begin .
pitr rollback ./
pitr diff 3689803651bb 3689803651bb --path ..
pitr revert 3689803651bb --path .././ --dry-run

cd /pitr_fs/data
pitr init .
pitr recover .
```

结果：

- `begin ..` 和 `commit .././` 都规范化为 `/workspace/relative-e2e`。
- `begin .` 在嵌套目录规范化为 `/workspace/relative-e2e/nested`，rollback
  删除探针文件。
- `logs`、`diff --path`、`revert --path --dry-run` 的相对路径均生效。
- `init .` 和 `recover .` 在挂载根幂等成功。
- 原 `/pitr_fs/data/acceptance/ready.txt` 保持不变，最终 0 active transaction。

实现保持 daemon 的绝对 scope 不变量：相对路径由 CLI/SDK 在 RPC 前解析；
宿主 wrapper 负责把 calw 的 `PITR_WORKSPACE` cwd 映射到容器 `/workspace`
cwd。新增单元与 wrapper 集成测试后，全仓未缓存 race、vet、build、buf 和
Python SDK 测试均通过。
