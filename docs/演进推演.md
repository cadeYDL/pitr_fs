# pitr-fs 演进推演

> 本文记录尚未进入当前产品承诺的架构推演，用来约束后续迭代方向，而不是描述
> 已经实现的功能。当前行为仍以 `README.md` 和《设计文档》的“当前权威语义”为准。

## 1. 结论

pitr-fs 后续沿两条主线演进：

1. **性能尽量对齐 JuiceFS**：先量化外层 FUSE、自动版本、审计和 PostgreSQL
   各自的成本，再逐步减少数据面复制、上下文切换和元数据往返；最终候选形态是
   把 pitr 能力注入固定版本的 JuiceFS 客户端，将两层 FUSE 收敛成一层。
2. **补齐 Agent 存储基建能力**：从单卷、单挂载、全局时间线，演进为能够表达
   租户、用户、Agent、Session 和共享工作区的隔离与协作系统。普通文件写入仍然
   自动形成可恢复历史，不重新引入要求业务显式调用的 `begin/commit`；跨文件、
   跨目录的一次业务变更通过未来的 `publish` 形成原子发布版本。

这两条线不是彼此独立的功能堆叠。Agent 并发会放大当前全局写窗口、元数据事务和
双层 FUSE 的成本；单层数据面则必须保留未来多会话所需的身份、隔离域和发布边界。

## 2. 当前基线与边界

当前实现可以概括为：利用 JuiceFS 的数据/元数据分离和数据对象不可变写入特性，
在 PostgreSQL 中维护历史元数据与 chunk/slice 的映射；历史版本在 slice 维度持有
物理引用，版本淘汰后释放引用并由 JuiceFS 原生 GC 删除不再可达的对象。

当前已经具备透明自动版本、目录回滚、时间回滚、历史裁剪、空间水位、slice 生命周期
和逻辑升级等能力，但仍有明确边界：

- 一个服务只管理一个全局卷和一个挂载点。
- 写入归属依赖全局串行的自动版本窗口，不适合多用户高并发。
- 用户路径经过 pitr-fs FUSE proxy 和 JuiceFS FUSE 两层用户态文件系统。
- 元数据创建约为 `10.13 ms/op`，底层 JuiceFS 约为 `2.07 ms/op`；256 MiB
  顺序写约损失 `16.78%`，顺序读的 pitr 层增量损失约 `3.85%`。
- 高频小文件、4 KiB 随机覆写和大规模 history 回放仍是弱项。
- 当前版本历史适合故障恢复和操作审计，还不能表达多个 Session 的私有视图、冲突
  检测和原子发布。

因此现阶段仍应视为验证核心机制的单机原型，不能直接宣称为多租户、分布式 Agent
存储平台。

## 3. 主线一：性能尽量对齐 JuiceFS

### 3.1 先拆分性能成本

当前生产基准测到的是完整 pitr 路径与底层 JuiceFS 的差异，其中同时包含：

```text
外层 FUSE 往返
+ proxy 的 inode/fd/路径转换与数据复制
+ 自动版本 open/close
+ history 触发器、WAL 与索引写放大
+ 审计采样和进程信息采集
+ 裁剪、引用计数和维护锁等待
```

在决定修改 JuiceFS 前，必须补齐三组相同负载的对照：

1. 原生 JuiceFS。
2. pitr-fs FUSE 纯透传，关闭版本、审计和裁剪。
3. 完整 pitr-fs。

第 1、2 组的差值才是第二层 FUSE 的成本，第 2、3 组的差值是版本系统成本。
需要分别记录顺序/随机读写、不同文件规模、元数据 p50/p95/p99、CPU、上下文切换、
数据复制、PostgreSQL RTT、WAL bytes/op 和 history rows/op，不能只比较带宽均值。

### 3.2 两层 FUSE 收敛为一层

当前链路：

```text
应用 → 内核 VFS → pitr-fs FUSE → POSIX → 内核 VFS
     → JuiceFS FUSE → JuiceFS VFS/Meta/Store
```

候选链路：

```text
应用 → 内核 VFS → 带 pitr 扩展的 JuiceFS FUSE
     → Operation Observer → JuiceFS VFS/Meta/Store
```

JuiceFS v1.3.0 没有覆盖全部 POSIX 写操作和提交生命周期的稳定公共 Hook。
`meta.Meta.OnMsg` 面向 `DeleteSlice`、`CompactChunk` 等内部消息，不能替代
Create、Write、Flush、Release、Rename 和 Unlink 的前后置观察。因此要真正去掉
外层 FUSE，需要维护一个小范围 JuiceFS 补丁，而不是只实现一个外部插件。

推荐采用双落点、单进程的扩展：

- **FUSE/VFS 边界**：识别用户意图、UID/GID/PID、fd 生命周期以及
  create/truncate/write/fsync/release/rename/unlink 等操作。
- **Meta 事务边界**：把 operation/version ID 传入 JuiceFS 已有的元数据事务，
  原子捕获真实变更，并区分用户操作和 Compaction。

FUSE 层知道“用户要做什么”，Meta 层知道“最终提交了什么”。只包装 `meta.Meta`
会丢失部分 POSIX 意图和 fd 生命周期；只在 FUSE 层观察又无法保证版本元数据和
JuiceFS 元数据原子提交。

### 3.3 预期收益

只减少一层 FUSE，可以消除一次内核/用户态往返、调度、数据复制和 proxy 映射，
但不会自动消除版本数据库事务。因此收益应分场景判断：

| 场景 | 只去掉外层 FUSE 的预期 | 若同时合并元数据事务 |
|---|---|---|
| 大文件顺序读 | 低个位数改善 | 额外收益有限 |
| 大文件顺序写 | 预计有中等改善 | 可减少版本边界等待 |
| 小文件/元数据 | 无法单独消除当前近 5 倍差距 | 可能成为主要收益来源 |
| 4 KiB 随机写 | 有意义但不是数量级提升 | 可减少每次写的 SQL/WAL 固定成本 |

这里是基于现有数据的工程推断，不是性能承诺。单层原型只有在同一环境的 A/B
基准中证明收益，才能进入生产架构。

### 3.4 正确性难点

一次业务命令不等于一次 FUSE 请求。例如 `echo x > f` 可能展开为 lookup、open、
truncate、write、flush 和 release；Write 返回时异步数据也不一定已经稳定提交。
单层改造必须继续覆盖：

- buffered write、direct I/O、mmap/writeback、fsync、flush 和 release。
- rename、hardlink 后的 inode 与路径解析。
- 同一进程并发写多个文件，以及一个文件被多个进程打开。
- 服务冻结后拒绝新写，并撤销升级前未完成写窗口的半成品。
- JuiceFS Compaction 与用户写入重叠时的版本归属、引用计数和回滚语义。
- 客户端崩溃、数据库事务失败、对象上传失败后的可见性和恢复。

性能提升不能以缩短可恢复历史、提前删除对象或放松原子性为代价。

### 3.5 上游版本与许可证边界

短期继续固定 JuiceFS v1.3.0 和 PostgreSQL 16.14，只依赖已有 ABI 校验覆盖的
字段、事务和编码，不追随上游日常升级。遇到阻断性安全或正确性问题时，再单独建立
新 ABI、数据迁移和全量回归计划。

JuiceFS Community Edition 使用 Apache License 2.0，允许修改、商业使用和以
源码或二进制形式分发，也不因修改本身强制公开源码。发行修改版时仍必须：

- 附带 Apache 2.0 License 并保留版权、专利和归属声明。
- 明确标记修改过的文件或补丁。
- 保留适用的 NOTICE 和第三方依赖许可。
- 不暗示 pitr-fs 修改版是 JuiceFS 官方产品，也不取得其商标权。

pitr-fs 主体继续采用 MIT License 不冲突，但正式发行包含修改版 JuiceFS 的镜像或
二进制前，需要补齐发行物的 Apache 2.0 许可、修改声明和第三方许可清单。

### 3.6 性能演进顺序

1. 建立原生、纯透传、完整 pitr 三段基线和持续性能门禁。
2. 减少自动版本 open/close、history 和裁剪的 PostgreSQL 往返。
3. 将完整 JSONB 旧行改成稳定的字段 diff/二进制格式，并批量写 history。
4. 做单层原型，只覆盖 Create/Write/Flush/Release/Rename/Unlink，验证收益和正确性。
5. 若原型达标，把 operation context 下沉到 Meta 事务，逐步覆盖全部 POSIX 边界。
6. 优化随机写的 slice 聚合、Compaction 调度与缓存，同时保持历史引用正确。

建议以“元数据延迟降低至少 20%～30%，或 4 KiB 随机写提升至少 25%，且完整
正确性套件通过”作为单层原型继续投入的参考门槛。最终长期目标不是绝对等于原生
JuiceFS，而是在开启版本能力时能够解释且约束每一项增量成本。

## 4. 主线二：面向 Agent 的存储基建

### 4.1 为什么仍然需要版本控制

Agent 会批量生成、覆盖、重命名和删除文件，且经常需要在工具失败、推理偏离、用户
拒绝结果或发布冲突后恢复。透明的文件级版本可以让未知工具和普通 POSIX 程序无需
接入 SDK 就获得 undo、审计和故障恢复，因此它仍是基础能力。

但仅让用户记住“每个文件修改前的版本”不够：一次业务变更通常跨多个文件甚至多个
目录，逐文件选择版本无法保证目录树处于同一个一致时刻，也容易漏掉新增、删除和
rename。未来需要同时保留两种粒度：

- **操作版本**：每次成功 POSIX 写入自动产生，用于细粒度 undo 和审计。
- **发布版本**：一个 Session 当前工作集跨文件、跨目录原子发布的逻辑修订，用于
  协作、交付和一致性恢复。

操作版本解决“刚才哪个写入错了”，发布版本解决“这次业务改动整体是否接受”。

### 4.2 不重新引入 begin/commit

未来多用户并发不要求用户手工执行 `begin/commit`。文件系统入口已经能够获得
UID、GID、PID，Agent 网关还可提供 tenant/user/agent/session 身份；系统应根据
身份自动把读写路由到独立工作域，普通 POSIX 操作继续自动形成历史。

建议的身份层级是：

```text
tenant → user → agent → session → workspace/domain
```

- `tenant/user` 决定授权、配额、加密和计费边界。
- `agent/session` 决定当前私有视图、审计归属和并发生命周期。
- `workspace/domain` 决定一组路径的基线、分支和发布目标。

不能只信任 Linux UID：容器、远程 Agent 和共享服务账号可能复用 UID。生产形态需要
由可信 Agent 网关签发不可伪造的 session context，并在进入文件系统时完成身份绑定。

### 4.3 会话隔离域与发布模型

建议把全局可见状态称为 `published`，每个 Session 在其基础上拥有私有工作域：

```text
                   ┌─ session A workspace ─ publish ─┐
published revision ├─ session B workspace ─ publish ─┼→ new published revision
                   └─ session C workspace ─ discard ─┘
```

基本语义：

1. Session 建立时记录一个 published revision 作为基线。
2. Session 内所有 POSIX 写入自动落入自己的工作域，其他 Session 默认不可见。
3. 同一 Session 的并发进程共享工作域，内部无需事务命令。
4. `pitr publish` 把相对基线的变更集跨文件、跨目录原子发布为一个全局版本。
5. 其他 Session 收到新 published revision 通知；未修改相关对象时可快速前移，
   已修改时进入冲突状态。
6. Session 可丢弃本地工作域、回退其中某次操作，或在冲突解决后重新发布。

“类似 MESI”适合作为可见性直觉，但不是要照搬 CPU cache line 协议。文件系统对象
存在目录树、rename、hardlink、大对象和长写入，实际需要 revision、lease、变更集和
冲突图，而不是 Modified/Exclusive/Shared/Invalid 四个状态的机械映射。

### 4.4 发布一致性与冲突

`publish` 至少需要满足：

- 发布内容以 Session 基线和当前工作域计算，不依赖用户手工列文件。
- 新建、修改、删除、rename、xattr 和目录结构作为一个变更集原子可见。
- 发布失败时 published revision 不变，Session 工作域仍可继续修改或重试。
- 检测基线之后其他发布是否修改同一 inode、目录项或相关 rename 路径。
- 文本文件未来可提供三路合并；二进制和目录结构默认要求显式选择。
- 读者可以钉住 revision 获得稳定视图，也可以订阅最新 published revision。
- 发布和回滚本身也形成审计事件，记录操作者、Session、来源 revision 和结果。

第一阶段可以采用乐观并发控制：允许任意 Session 私下修改，发布时对
`base revision → current published → workspace` 做冲突检测。需要避免把长时间文件
编辑变成持有全局锁。

### 4.5 隔离与共享资源

Agent 面向的资源可能完全隔离，也可能共享同一份代码、知识库或构建产物，因此
不能把“一用户一整套 JuiceFS”作为唯一模型。建议分层隔离：

| 层级 | 默认语义 | 典型用途 |
|---|---|---|
| 卷/存储池 | 强隔离，可使用独立密钥和对象前缀 | 不同租户、合规边界 |
| workspace | 独立 published 时间线和策略 | 项目、用户资源集合 |
| session domain | 私有可写视图 | 单次 Agent 任务 |
| shared revision | 只读或受控发布 | 多 Agent 协作基线 |

历史版本、空间额度和 GC 必须理解这些边界：共享 slice 只能在最后一个 workspace、
session 和历史版本都释放引用后删除；配额既要能显示用户可理解的逻辑文件容量，也要
避免跨租户去重泄漏资源存在性或造成计费不公平。

### 4.6 Agent 基建需要补齐的能力

按依赖顺序至少包括：

1. **身份与授权**：tenant/user/agent/session 身份、路径 ACL、只读/发布权限、
   不可伪造的审计主体。
2. **多卷与多挂载点**：一个控制面管理多个 workspace；挂载配置、配额和生命周期
   相互隔离，不能继续依赖唯一全局路径。
3. **会话视图**：基线 revision、私有 overlay、操作历史、discard 和稳定读取。
4. **原子发布**：跨文件/目录变更集、冲突检测、通知和幂等 publish ID。
5. **策略与配额**：全局策略向目录继承、子目录覆盖；版本数、时间、空间、I/O 和
   并发额度。
6. **事件与审计**：变更订阅、版本 provenance、Agent 工具调用关联、可检索 diff。
7. **运维能力**：指标、追踪、备份恢复、损坏检查、在线迁移、滚动升级和租户清理。
8. **SDK/网关**：POSIX 保持透明，同时为 Agent 编排层提供创建 Session、固定
   revision、publish、订阅和冲突处理 API。

## 5. 扩展到分布式需要解决什么

“对象存储是分布式的”不等于 pitr-fs 已经分布式。多客户端、多节点后还需要：

- **一致身份和路由**：同一 Session 的请求必须携带稳定身份，并路由到正确工作域。
- **分布式版本序列**：published revision 需要全局单调、幂等且可追踪，不能依赖
  单进程内存窗口。
- **元数据一致性**：明确采用单主 PostgreSQL、分片 PostgreSQL 或新的事务层；
  跨分片 publish 需要限制范围或引入协调协议。
- **lease 与 fencing**：节点失联、网络分区或进程暂停后，旧 writer 不能继续提交。
- **缓存失效与订阅**：发布、rename、权限和回滚必须使其他客户端及时感知；通知
  丢失后还能通过 revision 对账恢复。
- **幂等与重试**：Write、Close、Publish、GC 和 Revert 在超时重试后不能重复生效。
- **分布式 GC**：引用变更、版本裁剪和对象删除之间需要可恢复状态机；节点故障时
  宁可暂时泄漏，不能误删仍被任一 revision 使用的 slice。
- **热点与分片**：按 tenant/workspace 分片，处理超大共享 workspace 的元数据和
  WAL 热点，并定义跨分片 rename/publish 的限制。
- **灾备与安全**：元数据 PITR、对象版本/复制、密钥轮换、租户删除证明和多区域
  恢复点目标。

早期分布式形态应优先保持“单 workspace 的元数据事务位于一个分片”，不急于支持
任意跨分片原子发布。先通过 workspace 路由换取清晰一致性，再根据真实负载决定是否
引入更复杂的分布式事务。

## 6. 两条主线如何汇合

性能改造必须为 Agent 并发预留 operation context；Agent 模型也必须约束性能成本。
建议统一使用以下内部标识贯穿 FUSE/VFS、Meta、history、对象引用和审计：

```text
tenant_id
workspace_id
session_id
operation_id
base_revision
published_revision
```

单层 JuiceFS 原型如果只传递当前全局 version ID，将来还要重新修改一次核心写路径。
相反，一开始就把上述 context 作为不透明标识传递，当前单用户模式可使用默认值，
未来再逐步启用隔离和发布语义。

优先级建议如下：

| 阶段 | 性能主线 | Agent 主线 | 共同验收 |
|---|---|---|---|
| E0 | 三段成本基线、性能门禁 | 明确身份/Session/Revision 模型 | 当前正确性无回退 |
| E1 | 减少 SQL 往返和 history 写放大 | 多 workspace 控制面、只读 revision | 单机并发可观测 |
| E2 | 单层 JuiceFS 原型 | Session 私有工作域原型 | context 贯穿数据面 |
| E3 | 事务融合、随机写与缓存优化 | 原子 publish、冲突检测、通知 | 多 Agent 单机验收 |
| E4 | 分片、远端 PG/对象存储优化 | 多租户、配额、权限、网关 | 故障注入和恢复 |
| E5 | 多节点客户端与滚动升级 | 分布式 Session/Publish | 明确一致性与 SLA |

## 7. 暂不承诺的能力

以下内容在完成原型、性能和一致性证明前只作为研究方向：

- 任意跨租户或跨分片的原子 publish。
- 自动完成所有文本、二进制和目录结构冲突合并。
- 性能完全等同原生 JuiceFS且零版本成本。
- 无限历史或严格等于对象存储账单的实时空间预测。
- 多区域强一致写入和无中断基础运行时升级。
- 依靠命令行文本完整还原所有 Shell、IDE 和 mmap 写入的业务意图。

每项能力进入实现前，都需要补充语义、故障模型、迁移方案、性能预算和验收门槛，
避免把概念类比直接当成可交付设计。

## 8. 当前决策记录

- 默认保持自动版本，不恢复面向用户的 `begin/commit`。
- 文件级历史继续保留，但未来用 `publish` 表达跨文件、跨目录业务版本。
- Session 内并发属于同一私有域；不同 Session 默认互相隔离，只通过发布交换变化。
- 优先删除最老历史版本，版本数、空间和预留水位继续持久化配置。
- 生命周期保持 slice 精确引用、异步 JuiceFS 原生 GC；异常时宁可泄漏，不误删。
- JuiceFS/PostgreSQL 暂时固定版本，使用明确 ABI 边界，不为追随上游而升级。
- 单层 FUSE 是性能候选方向，不在没有成本拆分和原型数据时直接重构生产路径。
- Agent 基建先做单机多 workspace/session/publish，再扩展多节点和跨分片能力。
