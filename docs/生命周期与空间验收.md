## 真实挂载结果

使用用户绑定块目录，连续四次覆盖写入 8 MiB 文件：

| 指标 | 裁剪前 | 裁剪与 GC 后 |
|---|---:|---:|
| 用户版本数 | 5 | 1 |
| retained | 32 MiB | 16 MiB |
| reclaimable | 0 | 0 |
| 块目录实际字节 | 33,554,468 | 16,777,252 |
| 块目录文件数 | 9 | 5 |

配置为 `max-space=30MiB`、`space-reserve=20%`，高水位为 24 MiB。
系统按最老优先删除到 retained 低于高水位。裁剪前 `pitr space` 能识别共享
slice：部分版本 pinned 为 8–16 MiB，但当前单独删除预计释放为 0；最后一个
相关引用所在版本才显示实际边际释放量。

GC 周期临时设为 2 秒。最终 `pitr_gc_queue` 为空，到期且不再关联版本的合成
`jfs_delslices` 行为 0；唯一剩余的 PITR delslices 行属于当前保留版本，仍是
远期 pin。

## 可用性与安全检查

- 裁剪和 GC 前后文件 SHA-256 一致。
- delete-only GC 执行期间连续读取 60 次，失败数为 0。
- GC 日志包含 pending slice 删除和对象扫描，不包含 chunk compact。
- 对象目录实际收敛，不只是数据库引用计数变化。
- 重建容器并复用旧 PostgreSQL/块目录后，挂载、索引校准、空间配置和后续 GC
  均正常，覆盖旧卷升级路径。
- 指定 `PITR_BLOCK_PATH` 时没有创建默认数据 volume。
- `uninstall --purge` 删除数据库 volume，但明确保留用户块目录；验证后才单独
  清理隔离测试目录。

## 验收中修正的问题

初版例行 GC 使用 `--compact --delete`，真实挂载测试观察到 compact 当前 chunk
会带来不必要的读取扰动，因此改为 delete-only。随后确认版本释放不能直接删除
PITR 的 `jfs_delslices` 索引，而应把远期 pin 改成立即到期的待删记录；否则
部分 refs=0 slice 可能失去原生删除入口。最终方案已经针对这两个边界重新完成
全量和真实挂载测试。
