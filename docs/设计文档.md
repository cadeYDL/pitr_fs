# PITR-FS 设计文档

一个支持"自动版本控制"与"目录级时间回溯"的文件系统。底层复用 JuiceFS 提供 POSIX 语义,
版本能力通过 PostgreSQL 上的 MVCC 元数据扩展实现,写操作通过 FUSE **透明拦截**,不侵入用户程序。

---

## 当前权威语义：默认自动版本模式

本节覆盖文档后文仍保留的早期手工事务设计。后文的 `begin / commit /
rollback`、active transaction 和 commit 坍缩仅作为实现演进记录，不再是
对外行为。

- 系统始终处于自动版本模式，无需开启。每个由 FUSE 观察到的逻辑写操作
  都先打开一个独立 `auto` 版本，操作完成或写文件描述符关闭时立即关闭。
- `begin / commit / rollback` 已从 CLI 帮助隐藏；兼容 RPC/SDK 调用返回明确
  的“手工事务已停用”错误。
- `pitr revert <version>` 默认只作用于调用者当前目录；相对路径按调用者
  `cwd` 解析。只有显式 `--global` 才回退整个卷。
- 用户可见历史默认最多保留 100 个版本。通过
  `pitr config set history-limit <1..100000>` 修改，配置写入 PostgreSQL，
  daemon/容器重启后仍然有效。
- 当前控制面只允许全局 history limit。`pitr_config(scope_path,
  history_limit)` 与最长路径匹配查询已经支持未来目录配置：子目录继承
  最近父目录，子目录自身配置优先。
- `pitr clear --global --yes` 永久清空所有用户版本和 shadow history，
  但不改动当前 JuiceFS 数据；当前文件状态成为新的内部 root 基线，配置
  保持不变。
- 自动裁剪只删除已关闭版本；开放写窗口会阻止 clear、revert 和 umount。
  自动版本以全局时间线串行，保证 JuiceFS 独立数据库连接的触发器归属唯一。

```bash
# 任意普通写操作都会自动生成版本
printf 'v2\n' > result.txt
pitr logs .

# 默认回退当前目录；整卷回退必须显式声明
pitr revert 2c45c99418e8
pitr revert 2c45c99418e8 --global

pitr config set history-limit 100
pitr clear --global --yes
```

## 1. 目标与范围

- **主要目标**:让 Agent / 用户程序对文件系统做的任意写操作可回滚到任意历史时间点,粒度到子目录。
- **透明性**:用户程序用标准 POSIX API(open/write/rename/...) 即可,不需要调用任何 pitr 命令来写文件。
- **交互形态**:
  - `pitr` CLI:提供 init/revert/logs/diff/config/clear 等控制类命令。
  - `pitr` SDK:提供 Go / Python 两种语言 API,与 CLI 能力对等,便于嵌入 Agent 框架。
- **一期范围**:
  - 单机、单租户。
  - **透明 FUSE 拦截**写操作(一期核心难点)。
  - 全局串行开放写窗口，每个逻辑写操作形成独立版本。
- **未来范围**:同目录并发多事务 MVCC、跨租户 workspace、merge / rebase。

```
┌─────────────────────────────────────────────────────────────┐
│  pitrd (常驻 daemon,Go 实现)                                 │
│    · FUSE Server:拦截 15 类写操作,写前自动打点               │

│  /var/lib/pitr/jfs      │←──│  · JuiceFS 元数据表         │
│  (私有,用户看不到)      │   │  · pitr_* MVCC 表           │
│  数据 → 对象存储/本地   │   │  · history 触发器           │
└────────────────────────┘   └─────────────────────────────┘

                    ▲
                    │ gRPC over /var/run/pitrd.sock
        ┌───────────┴─────────────┐
        │                         │
┌───────────────┐         ┌───────────────┐
```

**关键分层**:
- **数据面**:用户程序 → FUSE(`/workspace`)→ pitrd 拦截 → JuiceFS 挂载点(`/var/lib/pitr/jfs`)→ 对象存储。用户程序只看得到 FUSE 挂载点,JuiceFS 挂载点是私有的。
- **控制面**:CLI / SDK → gRPC → pitrd,不走文件系统。时间旅行、配置与清理都由这条路径完成。
- **元数据面**:pitrd(和 JuiceFS 客户端)与 PG 直连,做事务打点和历史查询。

## 3. 关键设计决策

### 3.1 拦截层为什么是 FUSE 不是 eBPF

- FUSE 是标准用户态文件系统协议,可以**同步阻塞**去做 PG 打点,写前 COW 语义完整。
- eBPF 程序不能连 PG、不能睡眠,只能观察,做不到"写前打点后放行"。eBPF 在本项目中只作为**审计辅助**候选,不进入核心路径。

### 3.2 相对上版方案的修正

| 上版风险 | 上版做法 | 本版做法 |
|---|---|---|
| 禁 blob DELETE 破坏 JuiceFS | Trigger 静默返回 NULL | 不改 JuiceFS 表;`--trash-days 36500` + 关闭 `juicefs gc`,blob 只增不减 |
| Schema Clone 物理拷贝元数据 | `CREATE SCHEMA AS SELECT` | 影子表 + `txn_id` 触发器,零拷贝快照 |
| 自动打点节奏不清 | 未定义 | FUSE Write/Create/Unlink 等 handler 内在**修改前**同步打点;fd 级去重 |
| 目录 revert 深拷贝 | 挂只读快照 + rsync | 元数据层反向 replay 历史,只改 `jfs_edge/jfs_node` |
| 大表 TRUNCATE 回滚 | `TRUNCATE + INSERT SELECT` | history 反向应用,只影响真正改过的行 |
| PG PITR 概念混用 | 混为一谈 | 明确分层:pitr MVCC = 业务版本;PG WAL PITR = 灾备兜底 |

### 3.3 daemon 化 & 多语言 SDK

FUSE 挂载点必须由一个进程常驻持有,自然演化为 **daemon 架构**。CLI 与 SDK 都是 `pitrd` 的 thin client,通过 unix socket 上的 gRPC 通信。多语言 SDK 只需要 gRPC codegen + 少量包装。

### 3.4 元数据引擎为什么必须是 PostgreSQL

pitr 从元数据引擎需要三样东西同时具备:**同步触发器**、**本地事务原子性**、**jsonb 或等价的半结构化列**。缺一样都会让"写前 COW"这条链路断掉或膨胀。逐个候选评估:

| 引擎 | 同步触发器 | 事务 | 半结构化列 | 结论 |
|---|---|---|---|---|
| **PostgreSQL** | ✅ Trigger | ✅ | ✅ jsonb | 一等公民 |
| MySQL / MariaDB | ✅ | ✅ | ⚠️ JSON(功能弱、无 GIN 等价) | 可用但功能退化,无正收益 |
| SQLite | ✅ | ✅(全局写锁) | ⚠️ | 单进程原型可用;pitrd 多线程写就撞锁 |
| Redis | ❌ 只有异步 keyspace notification | ❌ MULTI 非钩子 | ❌ | 不满足 |
| TiKV / FoundationDB | ❌ | ✅ | ❌ | 不满足,需应用层实现钩子 |
| etcd / BadgerDB | ❌ | 部分 | ❌ | 不满足 |

**PG PITR 与 pitr 版本控制的关系**:PG 官方 PITR(WAL 归档 + `recovery_target_time`)是**整实例、离线、覆盖式**的时间回溯——回退期间 PG 停机、JuiceFS 客户端断连、无法子目录粒度、无多版本共存。它是**灾备兜底**,不能替代 pitr 的在线 + 目录级 + 多版本能力。两者独立分层部署。

**放弃 PG 的代价**:若坚持不用 PG,唯一现实的路是"pitrd 在应用层实现触发器"——每次写前主动 `KV.get(old)` → 记 shadow → 让底层写。代价是元数据延迟翻倍 + shadow 与主表跨系统无法原子,需要 WAL/两阶段补偿,复杂度陡增,一致性变弱。**没有必要**。

### 3.5 文件系统层为什么必须是 JuiceFS

pitr 方案能成立的地基是**"文件系统操作 = PG 表变更"**。JuiceFS 是目前把这两者优雅粘合的**最短路径**——它已经代我们做完了三件耗时且容易踩坑的事:

1. **POSIX ↔ SQL 的翻译层**:用户 `write()` → JuiceFS 翻译成 `UPDATE jfs_node/jfs_chunk`,我们才能在 PG 里装 trigger。
2. **成熟的 FUSE 服务端**:mmap / rename / xattr / hardlink / O_TRUNC 等十几个 POSIX 边缘 case 已经处理稳定,替代品要重写几万行。
3. **数据分块 + 对象存储 + 本地缓存**:chunk / slice / 引用计数,以及对 30+ 种对象存储的适配,拿走开箱即用。

替代方案的成本对比:

| 方案 | 一期工时 | 云原生 | macOS | 对象存储直连 | 备注 |
|---|---:|---|---|---|---|
| **JuiceFS + PG(当前)** | **4-5 周** | ✅ | ⚠️ FUSE VM 层 | ✅ | 最短路径 |
| 自造文件系统 | 6-12 个月 | ✅ | ⚠️ | ✅ | POSIX 边缘 case 是深坑 |
| ZFS / Btrfs snapshot | 1-2 周 | ⚠️ 需特权 | ❌ | ❌ 需中间层 | 完全另一条路,失去 PG trigger 优势 |
| rsync + hardlink | 3-5 天 | ⚠️ | ✅ | ❌ | 无 MVCC、不去重 |

**ZFS 备选方案的适用条件**:仅当目标场景是**纯 Linux 本地开发环境、无云端存储需求、能接受特权部署、无 macOS 支持要求**时,ZFS 路径能把工期压到 1-2 周,但架构与本文档描述的完全不同(不再需要 PG、trigger、shadow 表)。这是一条独立的技术路线,若选它需要单独立项。

**JuiceFS 的存储后端由用户自选**(见 §13):demo 用 `--storage file`,私有部署推荐 MinIO,云上推荐 S3 / OSS + Intelligent-Tiering。pitr 只做参数透传,不再封装一层存储抽象。

### 3.6 JuiceFS 对 PG 的写入语义(pitr 触发器的落点)

pitr 触发器要装在 JuiceFS 的表上,前提是理解 **JuiceFS 每次操作会往 PG 的哪些表写、写什么**。以下描述基于 JuiceFS 1.1+ 的 PG 元数据引擎 schema。

#### 3.6.1 数据 / 元数据分离

| 层 | 落在哪 | pitr 是否管 |
|---|---|---|
| **文件内容(blob)** | 对象存储 (`--storage file/s3/oss/minio`),按 chunk id 命名的 immutable object | 只保留(靠 `--trash-days` + `--no-bgjob` 兜底 GC),不写触发器 |
| **文件元数据** | PG 里的 `jfs_*` 系列表(见下) | **全部由触发器捕获** |

JuiceFS 每次文件写入只对元数据做**指针替换**——blob 本身 append-only、不覆盖旧对象。这是 pitr revert 能"只回滚元数据就恢复内容"的先决条件。

#### 3.6.2 JuiceFS 核心表全景

| 表 | 主键 | 存什么 | 何时被写 | pitr 是否接触发器 |
|---|---|---|---|---|
| `jfs_node` | `inode` | inode 元数据(mode/uid/gid/size/atime/mtime/ctime/nlink) | 创建/写/改权限/rename 会 INSERT/UPDATE/DELETE | ✅ 必须 |
| `jfs_edge` | `(parent, name)` | 目录项(父 inode + name → 子 inode) | mkdir/create/rename/unlink 会 INSERT/DELETE | ✅ 必须 |
| `jfs_chunk` | `id` (UNIQUE `(inode, indx)`) | 一个 inode 的第 `indx` 个 64MB chunk 由哪些 slice 组成(`slices` bytea 是 slice 序列的编码) | 每次 write 追加/替换 slice 时 UPDATE;文件删除时 DELETE | ✅ **必须(内容 revert 的关键)** |
| `jfs_chunk_ref` | `chunkid` | slice → blob 的引用计数(`refs`) | 新 slice 分配 INSERT;被覆盖时 `refs--` UPDATE;`refs=0` 后可能被 GC DELETE | ✅ **必须(否则 blob 被回收)** |
| `jfs_symlink` | `inode` | 符号链接的 target(bytea) | symlink() 时 INSERT | ⚠️ 尚未接(demo 未用到,生产按需) |
| `jfs_xattr` | `(inode, name)` | 扩展属性 kv | setxattr / removexattr | ⚠️ 尚未接 |
| `jfs_delfile` | `inode` | 延迟删除队列(等 nlink=0 且 open fd 关闭) | unlink 时可能 INSERT,GC 消费后 DELETE | ⚠️ 尚未接(与 revert 语义无直接关联) |
| `jfs_setting` / `jfs_counter` / `jfs_session*` | — | 全局配置 / 序列号 / 客户端会话 | JuiceFS 启动、format、客户端连接 | ❌ 不需要(与文件状态无关) |

#### 3.6.3 典型 POSIX 操作 → PG 表变更映射

| 操作 | 涉及表 | 变更 |
|---|---|---|
| `mkdir /d` | `jfs_node`, `jfs_edge` | INSERT node(dir);INSERT edge(root, "d", → dir inode) |
| `touch /d/f` | `jfs_node`, `jfs_edge` | INSERT node(file);INSERT edge(dir, "f", → file inode) |
| `echo x > /d/f` (覆盖) | `jfs_node`, `jfs_chunk`, `jfs_chunk_ref` | UPDATE node(size/mtime);UPSERT chunk(inode, 0) 指向新 slice;INSERT chunk_ref(新);UPDATE chunk_ref(旧 refs--) |
| `echo x >> /d/f` (追加) | 同上,但 chunk.slices 追加而不是替换 | 同上,旧 slice ref 不变 |
| `rename /d/f /d/g` | `jfs_edge` (可能 `jfs_node`) | DELETE edge(dir,"f");INSERT edge(dir,"g", 同一 inode) |
| `rm /d/f` (最后一条 nlink) | `jfs_node`, `jfs_edge`, `jfs_chunk`, `jfs_chunk_ref`, 可能 `jfs_delfile` | DELETE edge;DELETE/UPDATE node(nlink--);若无 fd 则 DELETE chunk + UPDATE chunk_ref(refs--) |
| `chmod / chown` | `jfs_node` | UPDATE node(mode/uid/gid/ctime) |
| `setxattr` | `jfs_xattr` | UPSERT |
| `symlink dst src` | `jfs_node`, `jfs_edge`, `jfs_symlink` | INSERT node(symlink type);INSERT edge;INSERT symlink(target) |

#### 3.6.4 对 pitr 触发器的推论

- **内容层 revert 的必要条件**:必须同时捕获 `jfs_chunk` + `jfs_chunk_ref`。只 revert `jfs_node/edge` 会导致"目录项恢复但读到最新内容"(demo 里已验证过这个负面 case)。
- **GC 抑制**:客户端 mount 必须带 `--no-bgjob`(禁后台压缩/清理),format 必须带 `--trash-days 36500`(等价于永不真删)。否则被 `refs=0` 的 slice 在 revert 到达之前就被删,blob 找不回。
- **写放大**:一次 `echo x > f` 会打出 ≥4 条 history(node UPDATE + chunk UPSERT + chunk_ref INSERT + 旧 chunk_ref UPDATE)。这决定了 shadow 表的增长速率——commit 坍缩(§6.1)必须能压缩这类"同一 chunk 反复覆盖"的序列。
- **未捕获表的语义损失**:`jfs_symlink` / `jfs_xattr` 未接触发器意味着 revert 到某个历史点后,symlink target / xattr 仍是当前状态。若业务不用这两类,可推迟到 P3 之后;若用,必须补。

## 4. 元数据模型

### 4.1 pitr 自有表

```sql
-- 版本 / 事务(同一实体的不同生命周期)
CREATE TABLE pitr_txn (
    id           bigserial PRIMARY KEY,
    version_hash char(12) UNIQUE NOT NULL,      -- 展示用短哈希
    parent_id    bigint REFERENCES pitr_txn(id),
    scope_path   text NOT NULL,                 -- 事务作用域(子树根)
    state        text NOT NULL,                 -- active | committed | rolled_back | auto
    command      text,                          -- 触发指令,如 "write:/a/b.txt"
    message      text,                          -- 用户 -m
    created_at   timestamptz NOT NULL DEFAULT now(),
    closed_at    timestamptz
);
CREATE INDEX ON pitr_txn (scope_path, state);
CREATE INDEX ON pitr_txn (created_at DESC);

-- 一个 scope 同时只能有一个 active 事务(一期约束,P3 放开)
CREATE UNIQUE INDEX uniq_active_txn_per_path
  ON pitr_txn (scope_path) WHERE state = 'active';

-- inode 影子表
CREATE TABLE pitr_node_history (
    txn_id       bigint NOT NULL REFERENCES pitr_txn(id),
    inode        bigint NOT NULL,
    op           char(1) NOT NULL,              -- I=insert / U=update / D=delete
    snapshot     jsonb,                          -- 旧行(U/D 时)或 NULL(I 时)
    recorded_at  timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (txn_id, inode)
);

-- 目录项影子表
CREATE TABLE pitr_edge_history (
    txn_id       bigint NOT NULL REFERENCES pitr_txn(id),
    parent       bigint NOT NULL,
    name         text NOT NULL,
    op           char(1) NOT NULL,
    snapshot     jsonb,
    recorded_at  timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (txn_id, parent, name)
);

-- blob 引用/保留(GC 用,一期预留)
CREATE TABLE pitr_blob_retention (
    object_key     text PRIMARY KEY,
    first_seen     timestamptz NOT NULL DEFAULT now(),
    retained_until timestamptz
);

-- chunk 影子表(装 trigger 到 jfs_chunk 后使用,见 §4.2)
CREATE TABLE pitr_chunk_history (
    txn_id       bigint NOT NULL REFERENCES pitr_txn(id),
    inode        bigint NOT NULL,
    indx         int    NOT NULL,               -- chunk 编号(inode 内)
    op           char(1) NOT NULL,
    snapshot     jsonb,
    recorded_at  timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (txn_id, inode, indx)
);

-- chunk blob 引用计数影子表
CREATE TABLE pitr_chunk_ref_history (
    txn_id       bigint NOT NULL REFERENCES pitr_txn(id),
    chunkid      bigint NOT NULL,
    op           char(1) NOT NULL,
    snapshot     jsonb,
    recorded_at  timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (txn_id, chunkid)
);
```

**关于 snapshot 存储量**

所有 `pitr_*_history.snapshot` 字段存的是**完整旧行 jsonb**,不是 WAL 指针也不是 diff。理由:自包含(任意时点直查即可,不依赖 PG 内部 xmin/lsn,不怕 vacuum);跨 JuiceFS 版本兼容(字段增减 jsonb 都吞得下);实现极简(一行 `to_jsonb(OLD)`)。

单行体积估算:

| 表 | 原始行 | jsonb 化后 |
|---|---:|---:|
| jfs_node  | ~120 B | 500-800 B |
| jfs_edge  | ~60 B  | 200-400 B |
| jfs_chunk | ~50 B  | 150-300 B |

不坍缩时,N 次连续写会产生 N 份 snapshot;坍缩后每个被改的 inode 只留一份原值(见 §6.1)。膨胀量的完整模型和缓解手段见 §6。

### 4.2 JuiceFS 表的桥接触发器

在 `jfs_node / jfs_edge / jfs_chunk` **三张表**上装 `BEFORE UPDATE OR DELETE` 触发器,把旧行推进影子表。

**为什么必须包含 `jfs_chunk`**:它维护 `inode → slice 列表` 的映射,覆盖写文件会更新它。若只抓 `jfs_node`(size/mtime)和 `jfs_edge`(目录项),回滚元数据后 chunk 仍指向新 slice → 用户读到的还是新内容,**版本回退在数据层失效**。demo(`demo/init.sql`)阶段为简化只装了 `jfs_node/jfs_edge`,生产版必须补上 `jfs_chunk`。

Trigger 通过 session 变量 `pitr.current_txn` 决定归属;pitrd 在触发写操作前先
`SET LOCAL pitr.current_txn = <id>`。变量为空(JuiceFS 内部 compaction 等)则不记录,
避免污染版本历史。

```sql
CREATE OR REPLACE FUNCTION pitr_capture_node_change() RETURNS TRIGGER AS $$
DECLARE
    v_txn bigint := current_setting('pitr.current_txn', true)::bigint;
BEGIN
    IF v_txn IS NULL THEN
        RETURN COALESCE(NEW, OLD);
    END IF;
    INSERT INTO pitr_node_history (txn_id, inode, op, snapshot)
    VALUES (v_txn, OLD.inode,
            CASE WHEN TG_OP = 'DELETE' THEN 'D' ELSE 'U' END,
            to_jsonb(OLD))
    ON CONFLICT (txn_id, inode) DO NOTHING;
    RETURN COALESCE(NEW, OLD);
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER tg_pitr_node_capture
BEFORE UPDATE OR DELETE ON jfs_node
FOR EACH ROW EXECUTE FUNCTION pitr_capture_node_change();
-- jfs_edge 同理,略
```

**`ON CONFLICT DO NOTHING`**:事务内同一 inode 多次改动只记第一次改动前的原值,后续中间状态无需保存。

> **实现偏离(Task 1.2 已合入)**:落地版触发器改成 **AFTER INSERT OR UPDATE OR DELETE**,原因是 AFTER 里 NEW/OLD 都稳定,且 INSERT 也可以捕获(op='I')供 revert 精确回删。GUC 解析被抽出到 `pitr_current_txn() STABLE` 函数集中处理空/非法值。`pitr_revert` 内部先 `SET LOCAL pitr.current_txn = ''` 抑制自身写入的打点,避免"revert 的 revert"。见 `internal/schema/init_pitr.sql`。

> **P0.3 最终结论**:JuiceFS 1.4.0 的 mount 进程不能接收 pitrd 已开启的
> PG transaction。生产路径采用单 daemon 串行的“开放 auto 窗口”:proxy
> 在写操作前提交一条 `state='auto', closed_at IS NULL` 的版本,独立连接上的
> trigger 在 GUC 为空时归属到该版本,操作完成后关闭窗口。`jfs_chunk_ref`
> 同步接入 history、坍缩和 replay。

## 5. FUSE 拦截层设计

### 5.1 挂载拓扑

```
用户可见:      /workspace          ← pitrd 的 FUSE 挂载
                    │ loopback 后端指向
私有 JuiceFS:  /var/lib/pitr/jfs   ← juicefs mount,由 pitrd 拉起
                    │
后端:          PG(元数据) + 本地或 S3(数据)
```

- `pitr init <path>` 期间,pitrd 先 `juicefs mount` 到 `/var/lib/pitr/jfs/<vol>`,再把 FUSE loopback 挂到用户指定的 `<path>`。
- 两层挂载都由 pitrd 生命周期管理:pitrd 停 → 卸载;pitrd 启动 → 恢复。

### 5.2 需要覆盖的 FUSE 操作

按"是否会改变文件系统状态"划分:

| 分类 | 操作 | 打点触发 |
|---|---|---|
| 元数据修改 | `Setattr`(chmod/chown/utimes/truncate)、`Setxattr`、`Removexattr` | 是 |
| 目录项修改 | `Create`、`Mkdir`、`Unlink`、`Rmdir`、`Rename`、`Symlink`、`Link` | 是 |
| 数据修改 | `Write`、`Fallocate` | 是 |
| 打开语义相关 | `Open(O_TRUNC)`、`Open(O_CREAT)` | 是(等价 Create/Truncate) |
| 无需拦截 | `Lookup`、`Getattr`、`Read`、`Readdir`、`Open(O_RDONLY)`、`Fsync` | 否 |

共约 15 个写类操作,统一走一个 `versionedHook(path, cmd, action)` 模板:

```go
func (n *Node) Write(ctx, fh, data, off) (uint32, syscall.Errno) {
    return n.versionedHook(
        n.path(),
        fmt.Sprintf("write:%s", n.path()),
        func() (any, syscall.Errno) {
            return n.LoopbackNode.Write(ctx, fh, data, off)
        },
    )
}
```

### 5.3 versionedHook 逻辑

```
1. 沿 path 向上找命中的 active 事务(最长前缀匹配 scope_path)
   → 若未命中,直接调用 action(),不打点
2. fd 去重检查:同一个 fd 在本 auto version 内已打过点,跳过打点
3. 起 PG 事务:
     a. INSERT pitr_txn (state='auto', parent_id=<txn>, command=<cmd>)
        → auto_version_id
     b. SET LOCAL pitr.current_txn = <auto_version_id>
     c. 调用 action()  ← 走到 JuiceFS,BEFORE 触发器捕获旧行到 history
     d. COMMIT
4. 记录 (fd, auto_version_id) 到 daemon 内存,用于去重
5. return action 结果
```

**关键点**:
- 打点 SQL 事务与 JuiceFS 写操作在**同一个 PG 事务**里,保证 history 和主表变更原子。
- 步骤 3c 里的 action 会导致 JuiceFS 客户端对 PG 执行 INSERT/UPDATE,触发器同步捕获——这依赖 JuiceFS 使用**同一个连接**。为此 pitrd 需要让 JuiceFS 客户端复用 pitrd 的连接池,或者 pitrd 直接以 JuiceFS meta 客户端 API 调用 PG 而非通过 mount 走一遍——具体在 P0 验证。若无法共享连接,退化方案是"打点在独立事务里,记录 begin/end 时间戳",一致性稍弱但可用。

### 5.4 打点粒度与性能

- **粒度**:一个 FUSE 操作 = 一个 `auto` 版本(带 fd 去重后,连续 Write 序列共享一个)。
- **性能预期**:每次首写多一次 PG round-trip,本地 PG 约 0.2–0.5 ms;命中 fd 去重后开销可忽略。
- **失败处理**:PG 打点失败 → 返回 EIO,写操作不落盘,POSIX 语义保持一致。

## 6. 版本保留策略

空间成本由两部分组成:**shadow 表膨胀**(元数据历史)和 **blob 保留**(数据历史)。本节定义 commit 时的坍缩机制和三档保留策略,让空间/能力可配置。

### 6.1 commit 坍缩

不做坍缩时,一次事务的每个 auto 版本各留一份被改行的旧值 —— N 次写产生 N × M 行 shadow(M = 被改的独立 inode 数)。commit 时可以合并:**每个 inode 只保留最早那一次改动前的原值**,后续中间状态全部丢弃。

坍缩后的膨胀率算式(T = 主表总行数,M = 事务内被改的独立 inode 数,N = 中间 auto 版本数):

| 模式 | 元数据冗余 | 数据(blob)冗余 |
|---|---|---|
| verbose(不坍缩) | 1 + N·M/T | 每次覆盖都保留(~N ×) |
| **compact(坍缩,一期默认)** | **1 + M/T ≈ 1× (小改动) 到 2× (大改动)** | **只留 commit 版 + begin 版 ≈ 2×** |

坍缩在 commit 的同一个 PG 事务里执行,元数据层原子:

```sql
-- 1. 同一 inode 在 begin→commit 之间只留最早的 snapshot
DELETE FROM pitr_node_history nh
WHERE txn_id IN (SELECT id FROM pitr_txn WHERE parent_id = <commit_id>)
  AND EXISTS (
      SELECT 1 FROM pitr_node_history older
      WHERE older.inode = nh.inode
        AND older.txn_id IN (SELECT id FROM pitr_txn WHERE parent_id = <commit_id>)
        AND older.id < nh.id);

-- 2. 精简后的 history 重挂到 commit 版本
UPDATE pitr_node_history SET txn_id = <commit_id>
WHERE txn_id IN (SELECT id FROM pitr_txn WHERE parent_id = <commit_id>);

-- 3. 删中间 auto 版本记录(pitr_edge_history / pitr_chunk_history 同理)
DELETE FROM pitr_txn WHERE parent_id = <commit_id> AND state = 'auto';
```

**语义 tradeoff**:坍缩后事务内的中间步骤(比如 auto_3)不再可 revert,只能回到 commit 或 begin。这与 git 一致——commit 之后 index 的中间状态就丢失了。

### 6.2 三档保留策略

| 策略 | 保留内容 | 空间冗余 | revert 粒度 | 适用 |
|---|---|---|---|---|
| verbose | 所有 auto 版本 | ~N× | 每一次写 | 调试、录制 Agent 行为 |
| **compact(默认)** | begin + commit | ~2× | commit 粒度 | 生产 |
| archive | 老 commit 超 D 天 merge 到 root | ~1× | 只保近 D 天 | 长跑控成本 |

卷级配置:`pitr config set retention {verbose|compact|archive} --window 30d`。

### 6.3 Blob 保留与 GC

- 格式化时 `--trash-days 36500` + 关闭 `juicefs gc`,blob 生命周期由 pitr 完全接管。
- `pitr_blob_retention` 表记录每个 object_key 的 `retained_until`。
- **compact 策略**:commit 坍缩后,把"中间 auto 版本产生但 begin/commit 都不引用"的 blob 打上 `retained_until = now()`。
- **异步 GC 服务**定期扫:找出 `retained_until < now()` 且 `pitr_*_history` 与 JuiceFS `jfs_slice_ref` 都不再引用的 blob,从对象存储真删。
- 一期先实现 compact 的**元数据坍缩**;blob 层 GC 留到 P4/P5(过渡期磁盘只增不减)。
- **崩溃安全**:元数据坍缩在 commit 事务内原子;blob GC 是外部动作,需幂等清理。

### 6.4 shadow 表物理优化(一期不做,后续可开)

- **按 recorded_at 月分区**:旧分区 detach 后压到 S3 冷盘,查老版本 attach 回来。
- **jsonb → 二进制**(msgpack 等):省 2-3 倍。
- **只存 diff**:比对旧新行只留变化字段。省 3-5 倍,但 revert 需要合并 diff 链。

## 7. 一致性语义

- **元数据一致**:任意 `commit` 或 `auto` 版本都对应一次完整的 FUSE 操作;pitrd 挂了 FS 就 EIO,不会有半态。
- **应用层缓冲**:事务内可写句柄从 Open 到 Release 独占一个 fd auto
  window;普通 `O_WRONLY` 同时使用 FUSE direct-I/O,确保每个 `write` 同步
  落在该窗口内,并避免每个 FUSE Write 都往返 PostgreSQL。无 active 时在
  fd 上缓存负判定。事务必须先 begin 再打开写 fd,且 commit 前关闭写 fd。
  上层 Flush 在关闭 auto 前显式 fsync 底层 fd,确保 JuiceFS chunk 元数据
  不会延迟到异步 Release 后才提交。
- **mmap**:一期支持只读和可写 mmap。可写 mmap 必须以 `O_RDWR` 打开,该类
  句柄不启用 direct-I/O,并复用 Open 到 Release 的 fd auto window,
  覆盖内核可能不单独通知 FUSE 的 mmap 脏页。为防止其他写误归属,该窗口
  生命周期内全局串行其他写操作;句柄未关闭时 commit 会因开放 auto 被拒绝。
  应用必须在 commit 前完成 `msync`、`munmap` 并关闭 fd。

#### 8.1.1 首次格式化与 `pitr init` 分工

一期的首次格式化发生在容器启动、pitrd 接受请求**之前**。`install.sh`
把存储配置作为环境变量传给 `deploy/entrypoint.sh`;entrypoint 仅在
`juicefs status` 判定卷不存在时执行一次 `juicefs format`,随后幂等安装
schema 和四张核心表的触发器。已存在的卷永远跳过 format。

| 安装参数 | 作用 |
|---|---|---|
| `PITR_STORAGE` | JuiceFS 存储后端,默认 `file` |
| `PITR_BUCKET` | bucket URL;file 后端默认容器内 `/data` |
| `PITR_VOLUME` | JuiceFS 卷名,默认 `default` |
| `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` / `PITR_SESSION_TOKEN` | 仅以环境变量透传的存储凭证 |
| `PITR_WORKSPACE` | 宿主机用户可见目录,容器内固定映射为 `/workspace` |
| `PITR_PG_VOLUME` / `PITR_DATA_VOLUME` | 持久化 PostgreSQL 元数据和 blob |

entrypoint 强制 `--trash-days 36500`;用户不能用运行时 RPC 覆盖。示例:

```bash
# 首次安装:file 后端

# 首次安装:S3(敏感值不落配置文件)

```

CLI 为兼容早期接口仍接受 `--storage/--bucket/--access-key/--secret-key/
--data-dir`,但运行时不会重新格式化或切换存储后端;存储变更必须重新部署并
显式迁移数据。卷配置由当前 pitrd 启动参数和 Docker volume 定义,不在
`~/.pitr/volumes/*.yaml` 另存一份可能漂移的副本。

#### 8.1.2 `pitr recover` 语义

**触发场景**:宿主机重启、`docker stop` 后重启、pitrd crash——PG 数据和
JuiceFS 卷仍在,但用户可见 FUSE 挂载可能丢失。`pitr recover` 是 daemon
内的恢复动作;容器不存在或未运行时先用 `install.sh recover`。

流程:

```
1. 按当前 pitrd 已知卷筛选全部卷或指定 <path>
2. 对每个卷:
     a. 验证 PG 可连、pitr schema 和 JuiceFS 元数据存在
     b. 不存在 → 报错,绝不 format
     c. 若上层 FUSE 未挂载 → 通过 daemon 的 mount callback 恢复
     d. 汇总卷名、底层/上层挂载和错误
3. 已挂载时幂等返回成功
```

**与 `pitr mount` 的区别**:`mount` 只恢复一个指定卷的上层 FUSE;
`recover` 会先做元数据健康检查并可批量处理当前 daemon 的全部卷。两者都
要求 daemon 已运行。

**与宿主机 `install.sh recover` 的分工**:install.sh 层负责**容器层恢复**
(容器停/删/kill 状态下 `docker start` 或复用 volume 重建),等待 socket
就绪后再调用容器内 `pitr recover`。见 §13.5。

### 8.2 事务与时间旅行

| 命令 | 作用 |
|---|---|
| `pitr begin <path> [-m msg]` | 在 `<path>` 开启事务 |
| `pitr commit <path> [-m msg]` | 提交 |
| `pitr rollback <path>` | 回滚到 begin 时状态 |
| `pitr revert <version> [--path <p>]` | 回到历史版本;`--path` 限定作用域 |
| `pitr logs [-n N] [--path <p>]` | 列出最近 N 个版本 |
| `pitr diff <v1> <v2> [--path <p>]` | 差异(预留) |

CLI、Go SDK 和 Python SDK 均接受相对路径，并在发起 RPC 前按客户端当前
工作目录转成规范化绝对路径；daemon 和数据库只保存绝对 scope，避免
`a`、`./a`、`x/../a` 形成多个逻辑范围。宿主机 wrapper 会把
`PITR_WORKSPACE` 内的当前目录映射到容器 `/workspace`：

```bash
cd /pitr_fs/data/proj
pitr begin .
pitr logs .
pitr commit .
```

若宿主当前目录不在 `PITR_WORKSPACE` 内，wrapper 以 `/workspace` 作为
相对路径基准；绝对的 daemon 路径（如 `/workspace/proj`）始终可用。
`diff/revert/recover` 的空 path 仍表示全局范围，不会被改写为当前目录。

## 9. 目录级 revert 算法

输入 `version_hash`,可选 `--path <p>`(默认全局)。

```
1. 解析 version_hash → 目标 txn_id = T_target
2. 找出 (T_target, HEAD] 区间内所有 scope 与 --path 有交集的 pitr_txn
3. LOCK TABLE jfs_node, jfs_edge IN EXCLUSIVE MODE
4. 先插入新 revert txn 并把 `pitr.current_txn` 设为其 id;按 id 逆序遍历
   这些 txn,对每条 history 记录:
     · op=U: snapshot 覆盖回主表
     · op=D: snapshot INSERT 回主表
     · op=I: DELETE 主表对应行
   若 --path 指定,只应用 inode 落在该子树内的行
5. replay 触发的变更由 trigger 捕获到新 revert txn,保存 revert 前状态。
   因此 revert 本身可被后续 revert 撤销,支持在历史版本间反复往返
6. COMMIT
```

只改元数据,不动 blob。

```go
func (c *Client) Revert(ctx context.Context, versionHash string, opts ...Option) error { /* ... */ }
```

```go

        cmdBegin(), cmdCommit(), cmdRollback(),

func cmdBegin() *cobra.Command {
    var msg string
    c := &cobra.Command{
        Use: "begin <path>", Args: cobra.ExactArgs(1),

            defer client.Close()
            txn, err := client.Begin(context.Background(), args[0], pitr.WithMessage(msg))
            if err != nil { return err }
            fmt.Printf("started txn %s @ %s\n", txn.VersionHash(), args[0])
            return nil

    c.Flags().StringVarP(&msg, "message", "m", "", "")
    return c
```

## 12. Python SDK

用 `grpcio` 从 proto 生成 stub,加一层符合 Python 习惯的包装(context manager)。

```python
# sdk/python/pitr/client.py
import grpc
from contextlib import contextmanager
from .pb import pitrd_pb2 as pb, pitrd_pb2_grpc as rpc

class Client:
    def __init__(self, socket: str = "/var/run/pitrd.sock"):
        self._chan = grpc.insecure_channel(f"unix://{socket}")
        self._rpc  = rpc.PitrdStub(self._chan)

    def begin(self, path: str, message: str = "") -> "Txn":
        r = self._rpc.Begin(pb.BeginRequest(path=path, message=message))
        return Txn(self, path, r.version_hash, r.txn_id)

    @contextmanager
    def transaction(self, path: str, message: str = ""):
        """with client.transaction(path) as txn: ...  出作用域自动 commit,异常自动 rollback"""
        txn = self.begin(path, message)
        try:
            yield txn
            txn.commit()
        except Exception:
            txn.rollback()
            raise

    def logs(self, path: str, n: int = 10) -> list:
        r = self._rpc.Logs(pb.LogsRequest(path=path, limit=n))
        return list(r.entries)

    def revert(self, version_hash: str, path: str | None = None): ...

class Txn:
    def __init__(self, client, path, version_hash, txn_id): ...
    def commit(self, message: str = ""): ...
    def rollback(self): ...
```

**用法**:

```python
from pitr import Client

client = Client()

with client.transaction("/workspace/src", message="edit parser") as txn:
    with open("/workspace/src/parser.py", "w") as f:
        f.write("...")
    # 异常时自动 rollback,正常结束自动 commit

# 时间旅行
for entry in client.logs("/workspace/src", n=10):
    print(entry.version_hash, entry.command, entry.message)

client.revert("a3f2c19b8e01", path="/workspace/src/parser.py")
```

### 13.2 `Dockerfile`(仓库根目录)

基础镜像用官方 `postgres:16`,复用它的 `docker-entrypoint-initdb.d/` 机制**首次启动自动执行建表 SQL**,无需外部脚本。

```dockerfile
# ---- 阶段 1: 构建 pitrd / pitr ----
FROM golang:1.22 AS builder
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -o /out/pitrd ./cmd/pitrd \
 && CGO_ENABLED=0 go build -o /out/pitr  ./cmd/pitr

# ---- 阶段 2: 运行镜像 ----
FROM postgres:16

# JuiceFS + FUSE + 基础工具
RUN apt-get update && apt-get install -y --no-install-recommends \
        ca-certificates curl fuse3 tini \
    && curl -sSL https://d.juicefs.com/install | sh - \
    && rm -rf /var/lib/apt/lists/*

# pitrd / pitr 二进制
COPY --from=builder /out/pitrd /usr/local/bin/pitrd
COPY --from=builder /out/pitr  /usr/local/bin/pitr

# 建表 SQL:两份拷贝
#   - initdb.d 目录里(PG 首次初始化时自动执行,只跑一次)
#   - /etc/pitr 目录里(entrypoint 后续幂等再跑,保证升级镜像时补丁生效)
COPY deploy/init_pitr.sql /docker-entrypoint-initdb.d/10-pitr-schema.sql
COPY deploy/init_pitr.sql /etc/pitr/init_pitr.sql

# 容器编排脚本
COPY deploy/entrypoint.sh /usr/local/bin/pitr-entrypoint.sh
RUN chmod +x /usr/local/bin/pitr-entrypoint.sh

ENV POSTGRES_USER=pitr \
    POSTGRES_PASSWORD=pitr \
    POSTGRES_DB=pitr_fs \
    PITR_VOLUME=default \
    PITR_MOUNT=/workspace \
    PITR_SOCKET=/var/run/pitrd.sock \
    PITR_DATA_DIR=/data

VOLUME ["/var/lib/postgresql/data", "/data"]
EXPOSE 5432

# tini 收养子进程,避免 PG 变僵尸
ENTRYPOINT ["/usr/bin/tini", "--", "/usr/local/bin/pitr-entrypoint.sh"]
```

要点:
- `10-pitr-schema.sql` 放到 `/docker-entrypoint-initdb.d/`,**PG 官方镜像会在数据目录为空时自动执行**——首次启动无需人工介入。
- 同一份 SQL 再拷贝到 `/etc/pitr/`,`entrypoint.sh` 在 PG 就绪后再 `psql -f` 跑一次(带 `IF NOT EXISTS`),保证镜像升级时新增 DDL 也能生效。
- 用 `tini` 做 PID 1,避免多进程僵尸。

### 13.3 `deploy/entrypoint.sh`

容器内三件事:拉起 PG → 幂等 apply 建表 SQL → 格式化 JuiceFS(首次) → 启动 pitrd。

```bash
#!/usr/bin/env bash
set -euo pipefail

# 1. 后台拉起 PostgreSQL(复用官方 entrypoint,它会处理 initdb + initdb.d)
docker-entrypoint.sh postgres &
PG_PID=$!

# 2. 等 PG 就绪
echo "[pitr] 等待 PostgreSQL 就绪..."
until pg_isready -h 127.0.0.1 -U "$POSTGRES_USER" -d "$POSTGRES_DB" >/dev/null 2>&1; do
    sleep 1
done

PG_DSN="postgres://${POSTGRES_USER}:${POSTGRES_PASSWORD}@127.0.0.1:5432/${POSTGRES_DB}?sslmode=disable"

# 3. 幂等再跑一次建表(补丁生效,不依赖 initdb.d 是否执行过)
echo "[pitr] 校准 MVCC schema..."
psql "$PG_DSN" -v ON_ERROR_STOP=1 -f /etc/pitr/init_pitr.sql

# 4. 格式化 JuiceFS 卷(仅首次;存储参数从环境变量透传给 juicefs)
if ! juicefs status "$PG_DSN" >/dev/null 2>&1; then
    echo "[pitr] 首次格式化 JuiceFS 卷 (storage=${PITR_STORAGE:-file})..."
    juicefs format \
        --storage "${PITR_STORAGE:-file}" \
        --bucket  "${PITR_BUCKET:-$PITR_DATA_DIR}" \
        ${AWS_ACCESS_KEY_ID:+--access-key "$AWS_ACCESS_KEY_ID"} \
        ${AWS_SECRET_ACCESS_KEY:+--secret-key "$AWS_SECRET_ACCESS_KEY"} \
        ${PITR_SESSION_TOKEN:+--session-token "$PITR_SESSION_TOKEN"} \
        --trash-days 36500 \
        "$PG_DSN" "$PITR_VOLUME"
else
    echo "[pitr] JuiceFS 卷已存在,跳过 format (recover 场景)"
fi

# 5. 启动 pitrd(前台,持有 FUSE 挂载 + gRPC socket)
mkdir -p "$(dirname "$PITR_SOCKET")" "$PITR_MOUNT" /var/lib/pitr/jfs
echo "[pitr] 启动 pitrd..."
exec pitrd \
    --pg-dsn "$PG_DSN" \
    --volume "$PITR_VOLUME" \
    --jfs-mount /var/lib/pitr/jfs \
    --fuse-mount "$PITR_MOUNT" \
    --socket   "$PITR_SOCKET"
```

`exec pitrd` 让 pitrd 成为容器的主进程,它挂了容器就退,不掩盖故障。PG 由 tini 兜底回收。

### 13.4 `deploy/init_pitr.sql`

> **实现路径(Task 1.2 已合入)**:权威源在 `internal/schema/init_pitr.sql`(供 `go:embed` 与 Go 集成测试用),`deploy/init_pitr.sql` 是 symlink 指向权威源,保留本节承诺的路径。Dockerfile 里 `COPY internal/schema/init_pitr.sql /docker-entrypoint-initdb.d/10-pitr-schema.sql` 直接从权威源拷贝,避免两份文件漂移。

包含第 4 节的全部 DDL,每条 `CREATE TABLE` / `CREATE INDEX` / `CREATE TRIGGER` 都写 `IF NOT EXISTS` 或先 `DROP ... IF EXISTS` 保证幂等。结构骨架:

```sql
-- pitr_txn / pitr_node_history / pitr_edge_history / pitr_blob_retention 见 §4.1
CREATE TABLE IF NOT EXISTS pitr_txn ( ... );
CREATE TABLE IF NOT EXISTS pitr_node_history ( ... );
CREATE TABLE IF NOT EXISTS pitr_edge_history ( ... );
CREATE TABLE IF NOT EXISTS pitr_blob_retention ( ... );
CREATE UNIQUE INDEX IF NOT EXISTS uniq_active_txn_per_path
    ON pitr_txn (scope_path) WHERE state = 'active';

-- 桥接触发器(依赖 JuiceFS 建好的 jfs_node / jfs_edge)
-- 注意:JuiceFS 表在首次 `juicefs format` 后才存在,所以这段包在 DO 块里做存在性检查
DO $$
BEGIN
    IF EXISTS (SELECT 1 FROM information_schema.tables WHERE table_name = 'jfs_node') THEN
        CREATE OR REPLACE FUNCTION pitr_capture_node_change() RETURNS TRIGGER AS $f$ ... $f$ LANGUAGE plpgsql;
        DROP TRIGGER IF EXISTS tg_pitr_node_capture ON jfs_node;
        CREATE TRIGGER tg_pitr_node_capture
            BEFORE UPDATE OR DELETE ON jfs_node
            FOR EACH ROW EXECUTE FUNCTION pitr_capture_node_change();
        -- jfs_edge 同理
    END IF;
END $$;

-- 根版本
INSERT INTO pitr_txn (id, version_hash, scope_path, state, command)
VALUES (0, '000000000000', '/', 'root', 'init')
ON CONFLICT DO NOTHING;
```

**关键顺序**:JuiceFS 表在 `juicefs format` 后才建。所以 `entrypoint.sh` 里"apply SQL"发生**两次**——第一次先建 pitr 自有表(此时 JuiceFS 表还不存在,DO 块跳过 Trigger);之后 `juicefs format`;然后 `pitrd` 启动时再 apply 一次(此时 JuiceFS 表已存在,补建 Trigger)。或者更简单:让 pitrd 启动前显式再跑一次 `psql -f init_pitr.sql`。

### 13.5 `install.sh`(仓库根目录)

```bash
#!/usr/bin/env bash
set -euo pipefail

IMAGE="${PITR_IMAGE:-pitr-fs:latest}"
CONTAINER="${PITR_CONTAINER:-pitrfs}"
WORKSPACE="${PITR_WORKSPACE:-$HOME/pitr-workspace}"
BIN_LINK="${PITR_BIN:-/usr/local/bin/pitr}"

sudo_if_needed() {
    if [ -w "$(dirname "$1")" ]; then echo ""; else echo "sudo"; fi
}

usage() {
    cat <<EOF
用法: $0 [install|recover|uninstall|status]
  install               构建镜像 + 启动容器 + 安装宿主机 pitr 命令(默认)
  recover               数据卷已存在时:重启容器 + 恢复挂载,**不 format**(见 §8.1.2)
  uninstall [--purge]   停止并删除容器/wrapper; --purge 一并清理数据卷
  status                查看容器状态
环境变量:
  PITR_WORKSPACE  宿主机工作目录 (默认 \$HOME/pitr-workspace)
  PITR_CONTAINER  容器名 (默认 pitrfs)
  PITR_IMAGE      镜像名 (默认 pitr-fs:latest)
  PITR_STORAGE    juicefs 存储后端 (默认 file);可选 s3/minio/oss/cos/...
  PITR_BUCKET     存储 bucket URL / 本地路径 (默认容器内 /data)
  AWS_ACCESS_KEY_ID / AWS_SECRET_ACCESS_KEY   云对象存储凭证(透传给 juicefs)
EOF
}

do_install() {
    command -v docker >/dev/null 2>&1 || { echo "错误:未安装 Docker"; exit 1; }
    docker info >/dev/null 2>&1        || { echo "错误:Docker daemon 未运行"; exit 1; }

    echo "==> 构建镜像 $IMAGE (首次约 3 分钟)"
    docker build -t "$IMAGE" .

    echo "==> 准备工作目录 $WORKSPACE"
    mkdir -p "$WORKSPACE"

    echo "==> 启动容器 $CONTAINER"
    docker rm -f "$CONTAINER" >/dev/null 2>&1 || true
    docker run -d --name "$CONTAINER" \
        --restart unless-stopped \
        --privileged \
        --device /dev/fuse \
        --cap-add SYS_ADMIN \
        --security-opt apparmor:unconfined \
        -v pitr_pgdata:/var/lib/postgresql/data \
        -v pitr_data:/data \
        --mount type=bind,source="$WORKSPACE",target=/workspace,bind-propagation=rshared \
        "$IMAGE"

    echo "==> 等待 pitrd 就绪 (最多 90 秒)"
    for i in $(seq 1 90); do
        if docker exec "$CONTAINER" test -S /var/run/pitrd.sock 2>/dev/null; then
            echo "    就绪"
            break
        fi
        sleep 1
        if [ "$i" = 90 ]; then
            echo "错误:pitrd 未在 90 秒内就绪,请查看日志:"
            echo "  docker logs $CONTAINER"
            exit 1
        fi
    done

    echo "==> 安装宿主机命令 $BIN_LINK"
    SUDO=$(sudo_if_needed "$BIN_LINK")
    $SUDO tee "$BIN_LINK" >/dev/null <<EOF2
#!/usr/bin/env bash
# pitr 宿主机 wrapper,转发到容器内的 pitr CLI
exec docker exec -it "$CONTAINER" pitr "\$@"
EOF2
    $SUDO chmod +x "$BIN_LINK"

    cat <<EOF

  ✓ 安装完成

  宿主机命令: pitr <cmd>
  工作目录:   $WORKSPACE   (容器内 /workspace)

  快速试用:
    mkdir -p $WORKSPACE/demo
    pitr begin  /workspace/demo -m 'try'
    echo hi > $WORKSPACE/demo/a.txt
    pitr logs   /workspace/demo -n 5
    pitr commit /workspace/demo -m 'done'
EOF
}

do_uninstall() {
    docker rm -f "$CONTAINER" >/dev/null 2>&1 || true
    if [ "${1:-}" = "--purge" ]; then
        docker volume rm pitr_pgdata pitr_data >/dev/null 2>&1 || true
        echo "  数据卷已清理"
    fi
    SUDO=$(sudo_if_needed "$BIN_LINK")
    $SUDO rm -f "$BIN_LINK"
    echo "  ✓ 已卸载"
}

do_status() {
    docker inspect -f 'container: {{.Name}}  status: {{.State.Status}}  started: {{.State.StartedAt}}' \
        "$CONTAINER" 2>/dev/null || echo "容器未运行"
}

do_recover() {
    # 场景 1: 容器 stop 状态 → docker start
    # 场景 2: 容器已删,但 pitr_pgdata / pitr_data volume 还在 → 复用 volume 重建容器
    # 场景 3: 容器在跑 → 只需 daemon 层 recover(pitr recover)
    command -v docker >/dev/null 2>&1 || { echo "错误:未安装 Docker"; exit 1; }
    docker info >/dev/null 2>&1        || { echo "错误:Docker daemon 未运行"; exit 1; }

    if docker inspect "$CONTAINER" >/dev/null 2>&1; then
        state=$(docker inspect -f '{{.State.Status}}' "$CONTAINER")
        if [ "$state" != "running" ]; then
            echo "==> 容器状态 $state,启动..."
            docker start "$CONTAINER" >/dev/null
        else
            echo "==> 容器已在运行"
        fi
    else
        docker volume inspect pitr_pgdata >/dev/null 2>&1 \
            || { echo "错误:pitr_pgdata volume 不存在,无法 recover;请用 $0 install"; exit 1; }
        mkdir -p "$WORKSPACE"
        echo "==> 容器不存在,复用 volume 重建..."
        docker run -d --name "$CONTAINER" \
            --restart unless-stopped \
            --privileged --device /dev/fuse \
            --cap-add SYS_ADMIN --security-opt apparmor:unconfined \
            -v pitr_pgdata:/var/lib/postgresql/data \
            -v pitr_data:/data \
            --mount type=bind,source="$WORKSPACE",target=/workspace,bind-propagation=rshared \
            "$IMAGE" >/dev/null
    fi

    echo "==> 等待 pitrd 就绪 (最多 90 秒)"
    for i in $(seq 1 90); do
        docker exec "$CONTAINER" test -S /var/run/pitrd.sock 2>/dev/null && break
        sleep 1
        if [ "$i" = 90 ]; then
            echo "错误:pitrd 未就绪,查 docker logs $CONTAINER"; exit 1
        fi
    done

    # 宿主机 wrapper 若被删,补装
    if [ ! -x "$BIN_LINK" ]; then
        SUDO=$(sudo_if_needed "$BIN_LINK")
        $SUDO tee "$BIN_LINK" >/dev/null <<EOF2
#!/usr/bin/env bash
exec docker exec -it "$CONTAINER" pitr "\$@"
EOF2
        $SUDO chmod +x "$BIN_LINK"
    fi

    # daemon 层 recover:让容器内 pitr 逐卷检查并挂载(不 format)
    docker exec "$CONTAINER" pitr recover
    echo "  ✓ recover 完成"
}

case "${1:-install}" in
    install)   do_install ;;
    recover)   do_recover ;;
    uninstall) do_uninstall "${2:-}" ;;
    status)    do_status ;;
    -h|--help) usage ;;
    *)         usage; exit 1 ;;
esac
```

### 13.6 平台差异

| 平台 | FUSE 挂载点在宿主机是否可见 | 说明 |
|---|---|---|
| Linux(内核 ≥ 5.x) | ✅ 可见 | `bind-propagation=rshared` 让容器内 FUSE 挂载事件回传宿主机,`$HOME/pitr-workspace` 就是 FS 入口 |
| macOS(Docker Desktop) | ❌ 宿主机不可见 | Docker Desktop 通过 VM 跑,FUSE 挂载在 VM 内,macOS 用户空间无法直接看到。**只能通过 `docker exec` 或 SDK 在容器内读写**——即宿主机 `pitr` 命令可用,但 `~/pitr-workspace` 里看不到 FUSE 内容 |
| Windows(WSL2) | ⚠️ WSL2 内可见 | 与 Linux 相同,但要在 WSL2 shell 里操作,不能通过 Windows Explorer |

**macOS 用户建议**:一期在容器内工作——`docker exec -it pitrfs bash` 进入后直接用标准 POSIX 命令。或者用 Python/Go SDK 在宿主机进程里操作(SDK 通过 unix socket forward 或 TCP 连 daemon,一期只支持 unix socket,所以宿主机 SDK 需要 `docker exec` 兜底或者本地部署 pitrd)。

透明的宿主机可见性问题是 Docker Desktop 架构固有限制,无法在一期解决。设计允许 P2 引入 NFS/9P 网关做 macOS 直连。

## 14. 未来演进

### 14.1 同目录并发多事务 MVCC(Phase 3)

- 每个 active txn 记录 `snapshot_txn_id`(快照起点)。
- 读操作按当前 txn 的 snapshot 从 `jfs_node + pitr_node_history` 计算视图(bi-temporal query)。
- commit 时冲突检测:若 history 里存在其他已 commit txn 改了同一 inode 且 commit_time > snapshot_time,本事务 commit 失败。
- 移除 `uniq_active_txn_per_path`。
- FUSE 层需要引入"事务上下文"概念——一个进程如何声明自己在哪个 txn 里读?候选方案:进程 cgroup/pid → txn 映射,或者 `pitr enter <txn>` 起 subshell 注入环境变量。

### 14.2 跨租户 workspace + merge/rebase

每租户一个 workspace schema,共享 `jfs_chunk/blob` 底座。`pitr merge / rebase` 做 history 三路合并。

### 14.3 PG 灾备

真正的 PG PITR(WAL 归档 + `recovery_target_time`)独立部署,作为整实例灾备兜底。

### 14.4 多目录规模化

一期一个 pitrd + 一个 PG 承载单机多目录足够;规模上去后有三条路,按扩展代价排序:

| 阶段 | 架构 | 单目录性能 | 运维复杂度 | 何时切 |
|---|---|---|---|---|
| a. 共享 PG(当前) | 一 PG × N 目录 | 4-8 ms/op(N × 100 万 inode) | 1 套 | 默认;适用 N ≤ 10 |
| b. **哈希分片** | M 套 PG × N 目录,`hash(scope)%M` 路由 | 2-4 ms/op | M 套(建议 M ≤ 10) | 单表超 500 万行 或 并发写吞吐撞 WAL 上限 |
| c. 隔离 PG | N 套 PG,一目录一 PG | 2-4 ms/op | N 套(运维成本随目录数线性) | 只在极端隔离需求(合规/多租户强隔离)时才走 |

**核心结论**:多目录扩展的正解是**分片**(b),不是**隔离**(c)。隔离方案每套 PG 至少 200 MB 内存 + 独立 catalog + 独立备份告警,K 个目录就是 K 倍固定开销;分片方案把目录哈希到 M << N 个 PG,单目录性能收益等同隔离,但运维成本控制在 M 以内。

**跨分片能力受限**:分片后如需 `pitr merge`/`rebase` 跨目录,涉及跨 PG 分布式事务,与 §14.2 合并到一起考虑。一期完全不涉及。

**一期总工时约 4–5 周**。

关键风险:
- **P0 共享连接问题**:若 JuiceFS 客户端不能复用 pitrd 的 PG 连接,Trigger 就抓不到 auto version 上下文——这是整个透明拦截方案的地基。必须在 P0 内验证清楚,否则退化到"打点独立事务 + 时间戳关联"方案,一致性稍弱但仍可用。
- **macOS 开发环境**:FUSE 在 macOS 需要 macFUSE(内核扩展),开发/CI 建议以 Linux 为主环境,macOS 只做客户端测试。
